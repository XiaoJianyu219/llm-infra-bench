## 08 · 单卡 profiling：MFU 28.4%，而 GEMM 跑到了峰值的 90%

**分母自己测**：bf16 GEMM 实测峰值 **155.57 TFLOPS**（规格 165.2 的 94.2%），
带宽 **948.4 GB/s**（规格 1008 的 94.1%），由此 **ridge point = 164.0 FLOP/byte**。

**分子手推**：线性层每 token forward 2×参数量、backward 的 dgrad 与 wgrad 各 2×，合计 **6N**；
attention 的两个 batched matmul 不含参数，单列 `12·L·d_attn·s`。

> **一个会静默出错的地方**：`d_attn = num_heads × head_dim = 16 × 128 = 2048`，
> 而 `hidden_size` 只有 **1024**。**两者差 2 倍**，代错会把 attention 项低估一半。

结果 **MFU 28.41%**（计入 lm_head 为 **34.95%**，两个口径都对）。

**bound 判定用三条互不依赖的证据**：

| 证据 | 数值 | 指向 |
|---|---|---|
| E1 算子时间构成（profiler） | GEMM 家族仅占 CUDA 时间 **37.2%**；optimizer 28.8% + elementwise 26.2% + softmax 5.8% + reduction 1.9% = **62.8%** | 时间不在算力上 |
| E2 GEMM 内部效率（profiler） | 这些 GEMM 自身达 140.5 TFLOPS = **实测峰值的 90.3%** | 算力侧已近上限，没有优化空间 |
| E3 batch 缩放（**不用 profiler**） | `step_ms = 114.3 + 19.7 × batch`；b=4 时固定开销占单步 **64.4%**；b1→b2 单步**不升反降** | 大半个 step 与计算量无关 |

> **"MFU 只有 28.4%"容易被读成"算力没吃满"——算子级数据说的是另一回事：
> 真正在做矩阵乘的 kernel 已经跑到峰值的 90.3%，它们只占 37.2% 的时间。
> 剩下 62.8% 的活算术强度远在 ridge point 之下，怎么加算力都不会变快。**

并排除了"CPU 下发跟不上"：profiler 记到的 CUDA self time 181.9 ms/步 vs 干净单步 187.8 ms，
**空泡 ≤ 3.1%**，每步 5,506 次 kernel launch，GPU 始终是满的。

**三个开关的净账**：

| 开关 | 吞吐 | 显存（allocated） | 净账 |
|---|---|---|---|
| bf16 AMP（对 fp32） | 4,875 → 9,909 tok/s（**2.03×**） | 18,345 → 16,645 MiB（**−9.3%**） | 提速一倍，显存几乎没省 |
| gradient checkpointing | 10,903 → 8,642（−20.7%） | 16,645 → 11,982（**−28.0%**） | 真正的价值是把 OOM 墙从 4,096 推到 12,288 token/步 |
| flash SDPA（对 math） | 8,966 → 11,539（+28.7%） | 19,328 → 16,644（−13.9%） | 同时更快更省；s=2048 时 math 直接 OOM |

**AMP 只省 9.3% 是最反直觉的一项**：参数、梯度、AdamW 两个 state 全是 fp32，
合计 **9.09 GB 与精度无关**，`autocast` 只改算子精度。

**MFU 与 HFU 必须分开**：开 checkpointing 后硬件多跑一次 forward，`HFU/MFU = 4/3 = 1.333`，
实测 **MFU 22.51% / HFU 30.01%**。
> **只看 HFU 会以为"硬件利用率从 28.4% 提到 30.0% 是改进"，而实际产出的 token 少了 20.7%。
> HFU 衡量硬件忙不忙，MFU 衡量有没有产出——选配置只能看 MFU。**

**显存墙只由每步 token 总数决定**：2,048 token 的四种 (s,b) 拆法显存差 **2 MiB**，
4,096 token 的三种拆法**全部 OOM**。主导项是 lm_head 输出的 logits
（`[tokens, 151936]`，交叉熵内部 upcast 到 fp32），**checkpointing 省不掉它**。
→ 正解是 chunked/fused cross-entropy，不是调 batch。

**"指定了"不等于"生效了"**：指定 cudnn 后端，实测跑的是 flash kernel（kernel 名、显存、吞吐全一致）。
后端身份一律按 profiler 里真实出现的 kernel 名判定。

## 09 · 并行策略对照：同样的切分，2.28 倍的差距

**先确认硬件事实，不采信文档**：`can_device_access_peer(0,1) = False`；
NCCL 日志 `Channel 00 : 0[0] -> 1[1] via SHM/direct`；`nvidia-smi topo -m` 为 **NODE**。
**两卡无直连，每个字节都要先写进主机内存再读回另一张卡。**

**实测通信带宽作为所有归因的分母**：all-reduce busbw @1 GB = **15.30 GB/s**
（NCCL 自估拓扑带宽 20 GB/s 的 76%），all-gather 12.69、reduce-scatter 12.72；
卡内 D2D **920.0 GB/s**。**卡间比卡内慢 60 倍。**

**六策略对照**（seq 512 / micro 2 / 每卡）：

| 策略 | 切了什么 | 显存 alloc | 理论 | 总吞吐 | weak 效率 |
|---|---|---|---|---|---|
| 单卡 micro2 | — | 12,013 MiB | 9,094 | 7,436 tok/s | 基准 |
| DDP | 不切 | 14,286 | 9,094 | 7,671 | **51.6%** |
| ZeRO-1 | 优化器状态 12N | 8,318 | 5,684 | 7,745 | 52.1% |
| ZeRO-2 | ＋梯度 | 8,318 | 5,116 | 8,535 | 57.4% |
| **ZeRO-3** | ＋参数 | **9,627** | 4,547 | **3,968** | **26.7%** |
| **FSDP** | 同 ZeRO-3 | **7,509** | 4,547 | **9,056** | **60.9%** |

**三处理论与实测对不上，每处都有具体原因**：
① 激活与 logits 约 2,900–3,200 MiB，**不被任何 ZeRO stage 切分**；
② DDP 多出的约 2,200 MiB 是精度组成不同（autocast 要为每个权重缓存 bf16 副本）；
③ **ZeRO-3 理论占用最低却实测最高**（+5,080 MiB）——all-gather 的常驻缓冲，
**在 0.6B 这个规模上缓冲区吃掉的比分片省下的还多**。
另：ZeRO-1 与 ZeRO-2 实测显存完全相同，因为 `contiguous_gradients: true` 预留了整块连续缓冲。

**FSDP 比 ZeRO-3 快 2.28 倍，差别不在算法**：

```
重叠系数 = Σ(所有 CUDA kernel 自时间) ÷ 干净单步时间
  FSDP   1.19  (中位)      通信被藏进了计算
  ZeRO-3 0.76               GPU 真实空泡 23.8%
通信 kernel 启动次数： ZeRO-3 405 次 vs FSDP 258 次（粒度更碎，更难摊薄延迟）
```

**用实测带宽交叉验证**：DDP 每步 all-reduce `4 × 596,049,920 = 2.384 GB`，
按 15.30 GB/s 预测 155.8 ms，profiler 实测 169.4 ms/步，**偏差 8.7%**。

**LoRA 下整张表塌掉**（可训练参数 0.764%）：DDP 的 weak 效率反而最高（**84.6%**，
因为梯度只有 18 MB，比全量的 2.38 GB **小 130 倍**）；ZeRO-1/2 只省 5.7% 显存；
**ZeRO-3 反而多用 14.4% 显存、吞吐只有 DDP 的 21%**。
→ **在这台机器上做 LoRA，正确答案是最朴素的 DDP。**

> **更根本的结论：双卡对全量微调几乎不值得**——最好的 FSDP 也只有 60.9% 的 weak 效率，
> **付出两倍的卡换来 1.22 倍的吞吐**。双卡的真正价值是**放得下原本放不下的东西**
> （每卡显存 12.0 → 7.5 GB）。

## 10 · 通信优化与归因拆解

**换机了，所以全部分母重测**：busbw 15.30→**12.37** GB/s（−19.2%）、
GEMM 155.57→**169.04** TFLOPS（+8.7%）、单卡吞吐 7,436→**6,029** tok/s（−18.9%）。
> 同型号两台机器，**算力更高但训练吞吐更低**——这个工作点是 launch/访存主导而非算力主导。

**先定噪声地板**：独立进程重复 10 次，吞吐极差 **1.87%**。

**扫描结果**：

| 类别 | 结果 |
|---|---|
| 有效提速 | 梯度累积 k=2/4/8/16 → +39.0 / +66.9 / **+89.8** / +97.9%；micro batch 4 → **+88.1%**；`NCCL_MIN_NCHANNELS=8` → +15.4%；`NCCL_NTHREADS=512` → +10.2%；fused AdamW +12.0%；`torch.compile` +8.2% |
| **有效减速** | `NCCL_PROTO=LL128` **−21.1%**（为小消息设计的旋钮用在 25 MB 级 bucket 上不是无效而是有害）；`NCCL_SHM_DISABLE=1` **−71.2%**（反向验证了 transport 判定） |
| **低于噪声地板** | 10 个 NCCL 设置里的 6 个 + 5 档 `bucket_cap_mb` + 3 个 DDP 开关，**共 14 个** |

**MIN 与 MAX 的区别是最有价值的一条**：`NCCL_MAX_NCHANNELS=8` 只抬高上限，
NCCL 依旧按拓扑选 2 个 channel，**+0.2%（玄学）**；`NCCL_MIN_NCHANNELS=8` 是**强制**用 8 个，+15.4%。

**`bucket_cap_mb` 无效有实测依据而非猜测**：从 chrome trace 取通信 kernel 的相对启动时刻，
p25/p50/p75 = **0.19 / 0.48 / 0.78**——**bucket 本来就分批触发、均匀散布，调度已经是对的**，
瓶颈不在调度（通信时间 215 ms 本身就大于可藏的 backward 窗口）。

**归因拆解用乘法分解，顺序无关**：

```
aggregate MFU = 单卡 MFU × 扩展效率
基线  10.68% × 54.8% = 5.85%
最终  36.85% × 86.4% = 31.82%      (5.44×)
取对数分账：单卡侧 73.1% / 通信侧 26.9%
```

**两组交互实验证明百分比不能相加**：

```
跨侧：k=8 (+86.8%) + micro4 (+88.0%)  实测 +265.1%   可加假设 +174.8%   超可加 +90.3 pp
同侧：k=8 (+86.8%) + MIN_NCHANNELS (+16.4%)  实测 +96.5%   可加 +103.2%   次可加 −6.7 pp
```

**方向相反，正是拆解必须做实验的理由。** 机制：每优化器步通信量恒为 4N 与 batch 无关，
两项分别把一次 all-reduce 覆盖的 token 数放大 8 倍与 2 倍，**放大倍数是相乘的**。

**梯度累积把通信瓶颈换成了 kernel launch 瓶颈**：k=8 的重叠系数掉到 0.64、GPU 空泡 36.1%；
k=8 每优化器步发 **46,325 次 kernel**（k=1 只有 5,879），按 10 µs/次推 ≈ 463 ms，
**实测空档 471 ms，吻合**。这解释了 k=16 相对 k=8 只多涨 8 个百分点，
也解释了 `torch.compile` 在 k=8 上值 **+45.9%** 而在基线上只值 +8.2%。

## 11 · 容错与断点续训

**先让训练可复现，判据才成立**：

| 模式 | 两次不中断运行的最大 loss 差 | 步时代价 |
|---|---|---|
| 默认 | **2.962e-3**（第 1 步就分叉） | — |
| `use_deterministic_algorithms(warn_only=True)` | 1.02e-2（**仍不一致**，只打告警不切实现） | +0.4% |
| `warn_only=False` + `CUBLAS_WORKSPACE_CONFIG=:4096:8` | **0.0（逐位一致）** | **+2.4%** |

非确定来源是 **Flash Attention 的 backward 默认非确定**。
> **不开严格模式，判据就得放宽到 3e-3，而那会掩盖掉下面 c1 那档 4e-3 的错误。
> 判据的精度必须高于要检出的缺陷。**

**三档完整度的恢复误差，症状可反查病因**：

| 版本 | 存了什么 | 首步差 | 最大差 | 症状 → 病因 |
|---|---|---|---|---|
| c0 | 权重 + 优化器 | **2.911** | 3.149 | 首步就差很大 → **数据顺序没恢复** |
| c1 | ＋数据位置 + step | **4.12e-2** | 1.165 | 首步小、之后单调变大 → **LR scheduler 没恢复** |
| c2 | ＋RNG + scheduler + 配置 | **0.0** | **0.0** | 逐位一致 |

第三种症状：单个 rank 对不上而其他对得上 → **只存了 rank 0 的 RNG**
（实测 rank1 恢复后 loss 11.271402 vs 掉卡前 11.316912；每 rank 另存 RNG 旁路后两边都逐位对齐）。

**体积账**：checkpoint **7.15 GB** 中优化器状态占 **66.7%**、模型权重 33.3%，
其余所有"小状态"（数据位置 128 B、RNG+scheduler+配置约 14 KB）合计只有 **0.0002%**。
> **"checkpoint 太大"的答案是优化器不是模型；而决定恢复对不对的正是那 14 KB。**

**Young/Daly 的推导与它的失效边界**：
`H(τ) ≈ δ/τ + τ/(2M)` → **`τ_opt = √(2δM)`**，最小开销 `√(2δ/M)`，
**最优点上保存开销与重算损失各占一半**。代入实测 δ = 5.923 s：
MTBF 1 天 → τ_opt **1,012 s**、开销 **1.17%**。

但**公式的常数 δ 假设会失效**：保存间隔 2 步时磁盘回写跟不上，
δ 被拉长到 **14.52 s**，实测开销 **539%** 而公式只预测 231%；间隔 16 步时回到与公式吻合 0.6 个百分点。

**"掉一张卡"是两种相差三个数量级的故障**：

| 故障 | 检测路径 | 实测 |
|---|---|---|
| `kill -9`（进程消失） | torchrun 的 elastic agent 监控子进程 | **0.44 s**（NCCL 超时根本没被触发） |
| `SIGSTOP`（活着但不响应） | 另一 rank 卡在 all-reduce 等超时 | **600 s 默认超时 + 约 92 s 尾巴 ≈ 11.5 分钟** |

**超时只能通过 `init_process_group(timeout=)` 设置**——
`TORCH_NCCL_TIMEOUT_MS` 这个环境变量**根本不存在**（查了 `libtorch_cuda.so` 里 24 个 `TORCH_NCCL_*` 变量）。

**弹性重启实测**：第一次重启**失败**在 DDP 构造的 `_verify_params_across_processes`（约 67 s），
第二次才成功 → **`--max-restarts` 至少要留 2 次**。
另：torchrun 只负责把进程拉起来，**它不知道训练状态**，恢复逻辑必须写在训练脚本里。

## 边界

- **最多 2 张卡、P=2**，all-reduce 的 busbw 与 algbw 恒等，该指标要 P≥4 才有区分度。
- **[09](../experiments/09-parallel-strategies/) 与 [10](../experiments/10-communication-tuning/) 在不同机器上**，数字不可直接比较。
- **只测了一个模型、一个 seq_len**；[09](../experiments/09-parallel-strategies/) 已说明
  ZeRO-3 的缓冲区开销与模型规模强相关，**7B 以上结论可能反转**。
- **DDP 与 DeepSpeed 的精度组成不同**（fp32 参数 + autocast vs bf16 参数 + fp32 主权重），
  总账都是 16N，但比较显存时这是一个未被消除的变量。
- **千卡外推依赖外部假设**，异步写**未实测**，NVLink 排名是**线性缩放外推**，
  详见 [limitations.md](limitations.md)。
