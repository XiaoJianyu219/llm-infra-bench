# 仓库规范

## 目录结构
days/dayNN/
├── report.md 结论、数据表、方法说明。面向读者。
├── journal.md 预测 vs 实测、判断错的地方、踩过的坑。面向自己。
├── results/ 该天产生的数据文件(json / tsv / log 摘要)
└── scripts/ 该天用到的脚本

根目录只放:`README.md`、`CONVENTION.md`、`BASELINE.md`、`JOURNAL.md`(索引)。

## 规则

1. **文件名固定为 `report.md` / `journal.md`**,不带日期或主题后缀。
   日期由目录名承载,主题写在文件的一级标题里。
2. **report 与 journal 分工明确。** report 写"得到了什么、怎么得到的";
   journal 写"预测了什么、错在哪、踩了什么坑"。两者不重复。
3. **每天的数据和脚本必须落在该天目录下**,根目录不再有 `results/`、`scripts/`。
   跨天复用的脚本(如 `simplify.py`)复制到每个用到它的天,
   以保证任意一天的目录可独立复现。
4. **预测先于测量。** journal 里的预测必须在跑之前写下,事后不得修改,
   只能在下方补"实测"与"判断错的地方"。
5. **敏感内容不进仓库。** 涉及未发表架构的类名、行号、对论文结论的影响,
   写在仓库之外,单独交付。

6. **每天收尾必须提交并推送。** 当天的 report、journal、results、scripts
   齐备后运行 `./finish_day.sh NN "一句话摘要"`,它会校验该天四件套是否完整、
   提交并 push 到 GitHub。没推送的一天视为未完成。
7. **事后补写的日志必须标注。** 文件开头写明"事后补记"及补写日期,
   并且只记录确实在测量前作出、事后被数据推翻的判断,不得补写未曾说出口的预测。
