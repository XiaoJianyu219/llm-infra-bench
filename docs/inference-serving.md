## 01 · 推理基线与测量纪律

**显存分解**（合计 22.22 GiB / 可用 23.13 GiB）：权重 16.79 GiB（75.6%）、峰值激活 2.26 GiB、
CUDA Graph 0.12 GiB、KV cache 3.05 GiB（13.7%）。

> **权重被所有请求共享只占一份，KV cache 每请求独占一份**——
> 所以并发上限由 KV cache 容量决定，与权重大小无关。

**KV cache 的单价与理论逐字节吻合**：实测 3.05 GiB / 22,208 tokens = **144 KiB/token**，
理论 `2(K,V) × 36层 × 8 KV头 × 128 head_dim × 2B = 147,456 B`。
由此可直接量化 GQA：若为标准 MHA（32 组 KV），每 token 576 KiB，
同样的池子只能装 5,552 个 token——**GQA 使可服务上下文提升 4 倍**。

**并发扫描**（req/s | TTFT_p50 | TPOT_p50）：

```
conc  1   0.42 |    229 ms | 17.3 ms
conc  4   1.36 |    416 ms | 19.7 ms
conc 16   3.45 |    844 ms | 28.5 ms
conc 64   3.52 | 13,814 ms | 32.4 ms
```

**吞吐在并发 16 附近饱和**：16→64 吞吐只涨 2%，而 TTFT_p50 涨 **16.4 倍**。
TPOT 只从 17.3 涨到 32.4 ms（不足 2 倍），**说明 decode 本身没被压垮，等待发生在进入批次之前**。

**单请求 decode 受显存带宽支配**：conc1 的 TPOT 17.3 ms ≈ 权重读取下限
`17.9 GB ÷ 1008 GB/s = 17.8 ms`。**此时算力大量闲置，这正是批处理能近乎免费提升吞吐的原因。**

**测量自洽性用 Little 定律验证**：四个并发档"并发÷吞吐"与"TTFT + 127×TPOT"偏差
2.0% / 0.7% / 3.8% / 1.4%，**全部 <4%**。

**一条容易被忽略的观察**：`nvidia-smi` 观测不到 KV cache 的真实使用量——
conc16 与 conc64 的显存峰值完全相同（22,215 MiB），因为 vLLM 启动时一次性预分配整个池子。
要看真实占用率必须读服务的 `/metrics`。

## 02 · KV cache 与服务参数

对 `gpu-memory-utilization` / `max-num-seqs` / `max-model-len` / `kv-cache-memory`
四组参数做单变量扫描。

**限制并发吞吐的是 KV cache 容量，不是调度器上限**：

```
KV tokens     15,088   22,208   25,376   27,712
conc64 req/s    3.10     3.60     3.76     4.00
```

单调递增无反常点，池子 +84% → 吞吐 +29%；
而 `max-num-seqs` 16→64 只 +8.4%、16→256 无进一步增益。

**收益递减来自 roofline 位置移动**：池子放大使有效 batch 增大，
TPOT 从 29.7 升到 43.7 ms，从带宽支配转入算力支配。
独立佐证：prompt 312 token 下，有无 KV cache 的**前向 token 数差 58.6×，耗时只差 2.10×**。

**"最大并发"类指标必须先确认分母**：`max-model-len` 8192→4096 使启动日志里的
`Maximum concurrency` 从 2.71× 跳到 **5.36×**，但实测吞吐 3.58 vs 3.60 req/s 在噪声内、
KV 池子也几乎没变。**那个指标按"每请求占满上下文的最坏情况"算，分母减半它就翻倍。**

**零代码调参成果**（conc64）：吞吐 3.32→4.00 req/s（**+20.5%**），
TTFT_p50 14,560→9,391 ms（**−35.5%**）。主要来自显式指定 `--kv-cache-memory`
榨干 `gpu-memory-utilization` 未覆盖的剩余显存。

## 03 · 连续批处理 vs 静态批处理

**实验设计**：两组服务处理**完全相同**的一份请求序列（200 请求、泊松 λ=4.0、固定 seed），
**仅调度策略不同**。对照组（HF transformers 静态批处理）也开了 KV cache 与 FlashAttention，
其吞吐在定长负载下只比 vLLM 低 17%——**是朴素实现而非劣化实现**。

| 负载 | 策略 | 吞吐 req/s | p50 | p99 |
|---|---|---|---|---|
| fixed | continuous | 3.82 | 2.4 s | 2.5 s |
| fixed | static | 3.27 | 9.3 s | 14.3 s |
| | **比值** | **1.17×** | 3.9× | 5.7× |
| varlen | continuous | 3.45 | 2.6 s | 12.2 s |
| varlen | static | 0.94 | 92.8 s | 165.4 s |
| | **比值** | **3.69×** | 35.7× | 13.6× |

**三条结论**：

1. **连续批处理的延迟严格正比于请求自身长度**：0.6/32 = 1.2/64 = 2.4/128 = 4.8/256 = 9.6/512
   = **18.75 ms/token**，截距约零。**每个请求只为自己要的东西付费。**
2. **静态批处理的延迟与请求自身长度无关**（82–95 s 之间浮动 13%）——这是"整批同时返回"的直接证据。
3. **优势主要来自处理长度不均的能力，不是批处理本身**（1.17× vs 3.69×，相差 3.2 倍）；
   **定长负载下代价体现在延迟而非吞吐，只报吞吐会严重低估差距。**

**延迟爆炸是过载的后果，不是批内等待的直接结果**：
批内取最大值 → 吞吐降到 0.94 → **到达率 4.0 > 服务率 0.94，过载 4.3 倍** → 队列无界增长。
批时长本身只有 17 s，而中位延迟 92.8 s。

**两处交叉验证**：批内最大值为 512 的概率 `1−(4/5)^16 = 97.2%` → 预测吞吐比 0.25，实测 **0.287**；
第 100 个请求落在第 7 批 → 预测延迟 94 s，实测 **94.2 s**。

## 04 · FP8 量化：一次失败的预测

**显存侧**：权重 16.65→10.18 GiB（−38.9%），KV cache 3.05→9.52 GiB（**+212%**），
KV tokens 22,208→69,312，**总占用几乎不变**（21,985 vs 22,041 MiB，都被 util 0.94 吃满）。

> **量化不是"省显存"，是在固定预算下重新分配显存。**
> 权重占比 75%→46%，KV 占比 14%→43%。
> 另注：**FP8 只量化权重，KV cache 仍是 bf16**，每 token 还是 144 KiB。

**性能侧**：conc1 吞吐 **0%**、TTFT −47%、TPOT +3.5%（噪声内）；conc64 吞吐 **+25%**、TPOT −18%。

**预测失败**：按带宽模型预测 conc1 的 TPOT 应从 17.2 降到 **10.5 ms**，实测 **17.8 ms**。
修正后的解释：vLLM 的 FP8 是 **weight-only** 量化，送入 GEMM 前要反量化，
该开销是纯计算、每步固定、不随 batch 变化：

```
batch=1（带宽支配）  节省带宽时间 ≈ 6.9 ms，反量化开销 ≈ 6–7 ms  → 抵消，TPOT 持平
batch≥4（转算力支配）Ada 原生 FP8 算力约 bf16 的 1.7–2×          → TPOT 降 17–18%
prefill（纯算力）    完全吃到红利                                  → TTFT 降 47%
```

> **+25% 的吞吐增益里带宽侧贡献为零**，全部来自 prefill 加速、KV 池扩大 3.1 倍、
> 以及大 batch 下 decode 的算力优势。**这与"权重小了读得快所以整体快"的直觉完全相反。**

**精度检验用 McNemar 配对而非均值直接比较**：bf16 90.75% vs FP8 89.50%，
仅 bf16 对 6 题、仅 FP8 对 1 题，**χ²=2.29 < 3.84，不显著**。
保持该比例需约 12 个分歧样本才能过阈，对应评测集要扩到 700–800 题。
（采用配对检验是因为独立比较在 n=200 下的显著阈值高达 7.6 个百分点，过于迟钝。）

## 边界

- 三个实验的载体、负载与机器不完全相同，**绝对值不可横向比较**，结论建立在组内对照上。
- [03](../experiments/03-continuous-vs-static-batching/) 只测了一种到达率（λ=4.0），
  轻载下差距应显著更小；静态侧走离散事件时钟不含 HTTP 开销，**报告的加速比是保守下界**。
- [04](../experiments/04-fp8-quantization/) 的反量化开销 6–7 ms 是**由抵消关系反推**，非直接测量；
  **AWQ-4bit 未跑**；`--kv-cache-dtype fp8` 未测试。
- 合成评测集只覆盖颜色识别与计数，**不可外推至 OCR、细粒度定位、复杂推理**。
