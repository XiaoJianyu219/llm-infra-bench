## 1. 五条预测（任务书 3.1，写于测量之前，不得修改）

模型取载体 A：Qwen3-0.6B，`N = 596,049,920`（Day 08 已手推并与
`named_parameters()` 逐字节核对；非 embedding 部分 440,467,456，
`tie_word_embeddings = true`）。

### 预测 0（分母，第 1 节要求先测的那个）

- **NCCL transport 会是 SHM（共享主机内存），不是 P2P。**
  40 系驱动禁用 PCIe P2P，`nvidia-smi topo -m` 单卡看不出来，
  但两卡到位后日志里应出现 `via SHM` 而非 `via P2P`。
- **2 卡 all-reduce 在 1 GB 消息下 busbw = 8 GB/s，区间 4–15 GB/s。**
  依据：PCIe 4.0 x16 单向理论 ~32 GB/s、实际 ~25 GB/s，
  经主机内存中转要走两趟（GPU→host、host→GPU），再打对折。
- **H2D / D2H（pinned）≈ 20 GB/s**（区间 16–24）。
- **D2D（卡内拷贝）≈ 870 GB/s** —— Day 08 实测同卡 copy 带宽 865.8 GB/s，
  这条基本是复现而非预测。
- P = 2 时 ring all-reduce 的 **busbw = algbw × 2(P−1)/P = algbw × 1**，
  即两者数值相等；这一点在 P=2 下失去区分度，report 里要写清楚
  （P≥4 时才拉开差距）。

### 预测 1 — DDP 双卡相对单卡的扩展效率（weak scaling）

**预测：扩展效率 58%，即加速比 1.16×。区间 45%–72%（0.9×–1.44×）。**

推理（这条推理如果错了，错在哪里比结论更重要）：

- Day 08 实测单卡 s512/b4（2048 token/步）单步 177.5 ms，其中 backward 约占 40%（≈70 ms）。
- DDP all-reduce 的是**梯度**。本日沿用 Day 08 的配置（fp32 主权重 + autocast），
  梯度是 fp32，体积 `4N = 2.38 GB`。
- 2.38 GB ÷ 8 GB/s ≈ **298 ms**，而整个 backward 只有 70 ms。
  **通信时间是可重叠窗口的 4 倍以上**，bucketing 最多藏掉 70 ms，
  剩下约 228 ms 完全暴露。
- 单步 177.5 → 约 406 ms，每卡吞吐降到 43.7%，双卡合计 87%。

按这条推理算出来是 **0.87×（不加速反而更慢）**。但我把点估计报成 1.16× 而不是 0.87×，
理由是：若 DDP 把梯度转成 bf16 再通信（`gradient_as_bucket_view` + bf16 comm hook
或框架默认按参数 dtype），体积减半到 1.19 GB，暴露时间降到约 80 ms，
加速比就回到 1.4× 左右。**我不确定这个实现细节，所以点估计取两种情形之间。**
实测时必须从日志确认梯度通信的 dtype 和总字节数——这正是归因的关键。

### 预测 2 — ZeRO-1 / 2 / 3 相对 DDP 的单卡显存降幅

理论值见第 2 节。**实测（`max_memory_allocated`）预测：**

| 策略 | 理论静态占用 | 相对 DDP 的理论降幅 | **预测实测降幅** |
|---|---|---|---|
| ZeRO-1 | 10N | −37.5% | **−20%**（区间 −14…−27%） |
| ZeRO-2 | 9N | −43.75% | **−24%**（区间 −17…−32%） |
| ZeRO-3 | 8N | −50% | **−28%**（区间 −20…−38%） |

实测降幅一定小于理论降幅，因为分母里还有不分片的部分：激活、
以及 Day 08 已证明在这个模型上是显存大头的 **logits `[tokens, 151936]`**。
按 Day 08 的 s512/b4 工作点，静态 16N ≈ 8.9 GiB，总 alloc 16.6 GiB，
静态只占 54%；把静态砍一半，总量只降 27%。

### 预测 3 — ZeRO-3 相对 DDP 的吞吐（本日题眼之一）

**预测：吞吐下降 60%（区间 −40% … −75%）。方向是降，不是升。**

ZeRO-3 每步的通信量远大于 DDP：

```
DDP        梯度 all-reduce 一次                          ≈ 4N（fp32 梯度）
ZeRO-3     forward  全部参数 all-gather                  ≈ 2N（bf16）
           backward 全部参数再 all-gather一次             ≈ 2N
           梯度 reduce-scatter                           ≈ 2N
           合计 ≈ 6N，且 all-gather 在关键路径上、粒度更碎
```

在有 NVLink（300–600 GB/s）的机器上，这 6N 相对于计算是可以被 prefetch 藏掉的，
所以论文里 ZeRO-3 的吞吐损失常报个位数百分比。
**在这台没有 P2P、走 SHM 的机器上，通信带宽低两个数量级，藏不住。**
这就是为什么我预测的降幅远大于常见文献值。

### 预测 4 — LoRA 场景下 ZeRO-1/2 的显存曲线形状（本日另一个题眼）

**预测：LoRA 下 ZeRO-1 与 ZeRO-2 的显存曲线是一条几乎水平的线 ——
相对 DDP 的节省小于 2%，基本看不出 stage 之间的差别。**

理由：ZeRO-1 切的是优化器状态，ZeRO-2 再切梯度，而 LoRA 下
**这两样东西都只跟可训练参数走**。设 adapter 占比 r（典型 0.1%–1%）：

```
冻结基座   bf16 参数 2N        常驻，无梯度、无优化器状态、不被 ZeRO-1/2 切分
adapter    2rN + 2rN + 12rN = 16rN
ZeRO-1 能省  12rN × (1 − 1/P)
ZeRO-2 再省   2rN × (1 − 1/P)
```

r = 0.5%、P = 2 时，ZeRO-1 省 `6rN = 0.03N`，而总常驻约 `2.08N`，
**节省 1.4%**。ZeRO-2 再省 0.24%。

**所以"LoRA + ZeRO-1/2"这个组合在显存上几乎是白搭。**
LoRA 下唯一有意义的是 **ZeRO-3**，因为只有它切冻结基座的那 2N 参数，
预测能省接近 `2N × (1 − 1/P) = N`，即约 48% 的常驻部分。
但代价是每步都要 all-gather 整个基座——在这台机器上大概率得不偿失。

**推论（一并记下，便于事后检验）**：如果实测发现 LoRA 下 ZeRO-1/2 省了 10% 以上，
那一定不是优化器分片省的，要去查是不是 DeepSpeed 顺手改了别的东西
（例如把基座也转成了 bf16、或者换了 activation checkpointing 默认值）。

### 预测 5 — FSDP(FULL_SHARD) 与 ZeRO-3 实测会不会一致

**预测：显存一致（差值在 ±5% 以内），吞吐不一致，FSDP 比 ZeRO-3 快 5%–15%。**

两者原理相同（参数、梯度、优化器状态全分片），所以显存应该对得上。
吞吐上我预测 FSDP 略快，理由是它的 all-gather / reduce-scatter 直接由
PyTorch 原生调度、与 autograd 引擎同一套流，
而 DeepSpeed 有自己的一层 partition 管理和参数协调开销。

**但这条预测的前提是 wrap policy 正确。** 任务书 4.4 说 wrap policy 错了
性能差数倍且不报错——若实测 FSDP 反而慢数倍，第一怀疑不是"FSDP 不如 ZeRO-3"，
而是我的 `transformer_auto_wrap_policy` 没生效。届时先打印被 wrap 的模块数
（Qwen3-0.6B 应当是 28 个 `Qwen3DecoderLayer` + 根模块，而不是 1 个）。

### 2.1 全量微调，混合精度 + AdamW

每参数 16 字节：bf16 参数 2 + bf16 梯度 2 + fp32 主权重 4 + Adam m 4 + Adam v 4。

| 策略 | 切分了什么 | 每卡公式 | P=2 的系数 | 每卡字节 |

### 2.2 LoRA，可训练比例 r

| 策略 | 每卡公式 | r=0.5%, P=2 | 相对 DDP |

## 5. 判断错在哪

### 5.1 最重要的一处：把"原理等价"当成了"实测会接近"（预测 5）

我预测 FSDP 与 ZeRO-3 显存一致、吞吐差 5–15%，理由是"两者原理相同，
差别只在实现开销"。实测吞吐差 **2.28 倍**。

错的不是"原理相同"这个判断——它们确实切分同样的张量、通信量也基本相同（都约 3.6 GB/步）。
错在我**默认原理相同就意味着实测接近**，而没有把"通信能不能藏进计算"当成一个
独立的、可能起决定作用的变量。实测：

```
FSDP   重叠系数 1.19（中位）  →  通信被藏进计算
ZeRO-3 重叠系数 0.76        →  没藏住，GPU 空等 23.8%
```

**在一条 15 GB/s 的链路上，通信藏不藏得住比切分方案本身更能决定吞吐。**
这条如果只看 3.3 的矩阵是看不出来的，必须做 3.5 的重叠分析才能归因——
任务书把 3.5 排在优先级 6，但它其实是解释 3.3 的钥匙。

另外值得记：我在预测 5 里还写了一条"若实测 FSDP 反而慢数倍，第一怀疑是我的
wrap policy 没生效"。实际方向相反（FSDP 快得多），而我仍然按任务书 4.4 验证了
被 wrap 的模块数 = 29（28 层 + 根模块）。**预先写下"如果结果异常先怀疑什么"，
在结果不异常的时候也值得执行一遍**——否则 FSDP 这个"好得出乎意料"的结果
本身就会变成一个没验证过的可疑项。

### 5.2 ZeRO-3 的显存比 ZeRO-1/2 还高，我完全没预料到（预测 2d / 4b）

理论上 16N/P < 9N < 10N，ZeRO-3 应该最省。实测 ZeRO-3 9,627 > ZeRO-1/2 8,318，
LoRA 下更夸张——ZeRO-3 比 DDP 还多用 14.4%。

原因是 all-gather 的常驻缓冲（`stage3_prefetch_bucket_size`、
`stage3_max_live_parameters` 控制）。**我在写理论账时把"切分后每卡该有多少"算得很仔细，
却完全没有给"为了切分而必须付出的缓冲区"留位置。**

而且这个开销**与模型规模不成比例**：0.6B 模型的参数本身只有 1,137 MiB（bf16），
切一半省 568 MiB，而缓冲区是按 bucket 大小配的常数级开销，直接把收益吃光。
**分片的收益随 N 线性增长，缓冲区开销却不是——所以模型越小，ZeRO-3 越不划算。**
这条在 7B 以上很可能反转，本日没有条件验证，已写进 report 的局限。

### 5.3 ZeRO-1/2 的显存收益被我低估了一倍（预测 2a/2b）

我按"静态占比 54%，砍一半 → 总量降 27%"折算，得到 −20%。实测 −41.8%。

漏掉的是分母侧：DDP 走的是 fp32 参数 + autocast，autocast 会为每个权重额外缓存
一份 bf16 副本（2N = 1,137 MiB），而 DeepSpeed 的 bf16 模式参数本身就是 bf16，
没有这份缓存。**所以 DDP 的基数比我算的大，降幅自然比我算的深。**
我在预测时把 DDP 和 ZeRO 的"每参数 16 字节"看成同一件事，
忽略了 16 = 4+4+4+4 与 16 = 2+2+4+4+4 在实际分配器上的差别。

### 5.4 带宽与 PCIe 都预测偏低（预测 0b / 0c）

与 Day 08 低估 GEMM 峰值（预测 138、实测 155.6）是**同一个方向的系统性偏差**：
我在给硬件可达值时总是比实际保守 10%–90%。
连续两天都往同一个方向错，说明这不是随机误差，而是我对"实际能跑到规格的百分之多少"
的先验偏低。下次给区间时应当把上界提到规格值的 90%–95%，而不是 80%–85%。

### 5.5 预测 1 的点估计不如我自己写的备用推理准

我在预测 1 里写了两条推理：主推理（若梯度 bf16）得 1.4×，备用推理（若梯度 fp32）得 0.87×，
最后点估计取了两者之间的 1.16×。实测 **1.03×**，离备用推理更近。

事后看，我当时其实有能力确定梯度是 fp32 的——本日 DDP 沿用 Day 08 的
fp32 参数 + autocast，梯度必然随参数为 fp32。**我把一个可以查清的事实当成了不确定项，
然后用"取中间值"掩盖了它。** 正确做法是先确定 dtype 再给单一预测。
（实测 4.1 的交叉验证也证实了这点：2.384 GB ÷ 15.30 GB/s = 155.8 ms，
profiler 实测 NCCL kernel 169.4 ms，吻合在 9% 以内——这正是 fp32 梯度的体积。）

### 5.6 预测 4 定性全中，定量差 3–4 倍

"LoRA 下 ZeRO-1/2 的显存曲线是平的、且两者几乎相同"——实测 ZeRO-1 与 ZeRO-2
**完全相同（4,435 MiB，一个字节不差）**，相对 DDP 省 5.7%。
手推给的是 1.4%/1.7%。多出来的部分不是优化器分片省的，
而是 DeepSpeed 顺带省掉的常驻缓冲。这正好落进我预测时写下的那句
"如果实测发现省了 10% 以上，那一定不是优化器分片省的" —— 5.7% 还没到 10%，
但成因确实不在优化器分片上。

## 6. 踩的坑

### 6.1 `init_process_group` 只按 `WORLD > 1` 判断，单卡调通阶段全线失败

按任务书 §0"先把所有脚本在单卡上调通"，我用 `torchrun --nproc_per_node=1` 跑，
此时 `WORLD_SIZE=1`，我的条件跳过了 `init_process_group`，
于是 DDP / ZeRO / FSDP 全部报
`ValueError: Default process group has not been initialized`。
条件改成 `strategy != "single" or WORLD > 1`。
**单卡调通本身会触发一类双卡不会触发的 bug**，这一步没白做。

### 6.2 DeepSpeed 默认 FusedAdam 要 ninja；换成 torch AdamW 反而是对的

`"type": "AdamW"` 会走 DeepSpeed 的 FusedAdam，需要 ninja 做 JIT 编译，本机没装，
直接报 `Unable to JIT load the fused_adam op`。

可以装 ninja，但**不装才是对的**：DDP 与 FSDP 用的都是 `torch.optim.AdamW`，
如果只有 ZeRO 换成 FusedAdam，吞吐对照就不是单变量了。
Day 08 实测优化器占单步 CUDA 时间约 29%，换个 kernel 足以改变结论。
改为在三个 config 里设 `torch_adam: true`，并把这个理由写进 config 的 `_optimizer_note`。

### 6.3 comm_bench 的集合操作不配对，NCCL watchdog 等满 600 秒后 SIGABRT

第一次跑第 1 节，所有带宽都测完了，**结果 json 没写成**。
根因是我自己写的：`pcie_bench()` 只在 rank 0 上调用（H2D/D2H/D2D 是本地测量），
但它内部复用的 `timeit()` 无条件调 `dist.barrier()`。
于是 rank 0 进了一个 rank 1 永远不会进的 barrier → 集合操作顺序不一致 →
NCCL watchdog 600 秒超时 → `exitcode -6 (SIGABRT)`。

NCCL 的报错原文直接点出了这件事：
> "This is most likely caused by incorrect usages of collectives, e.g., wrong sizes
> used across ranks, **the order of collectives is not same for all ranks**"

修法是给 `timeit` 加 `sync_ranks` 参数，本地测量传 `False`。
**任务书 4.2 只说了"只让 rank 0 写文件"，这个坑是它的近邻但更隐蔽：
只让 rank 0 做的事情里如果夹了一个集合操作，整个作业会挂 10 分钟然后崩，
而且崩在最后一步，前面的测量全部白做。**

### 6.4 重叠系数一开始被我当成了"空泡"，负数才让我发现

第一版 profile 脚本把 `Σ(CUDA kernel 自时间) / 干净单步时间` 当作 GPU 占用率，
超过 1 的部分记成"负空泡"，于是 DDP 报 −27.5%、FSDP 报 −79.2%。
**是负数才让我意识到公式的前提错了**：NCCL 通信 kernel 跑在独立 stream 上、
与计算 kernel 并发，各 stream 自时间之和本来就可以超过墙钟时间。
改成"重叠系数"：>1 是重叠量，<1 才是真空泡。

改完之后 ZeRO-3 的 0.76 才显出意义——它是四个策略里唯一小于 1 的，
即唯一有真实空泡的。**如果第一版的负数没有出现，我可能会把 −27.5% 当成某种
测量噪声糊弄过去，那样 ZeRO-3 的 +25.6% 空泡也就失去了参照。**

### 6.5 ZeRO-1 与 ZeRO-2 的显存一个字节都不差

理论上 ZeRO-2 比 ZeRO-1 多切梯度（2N/P，应省 568 MiB），实测两者都是 8,318 MiB。
原因是 config 里的 `contiguous_gradients: true` 会预留一块完整的连续梯度缓冲，
把分片省下的那块又占了回去。**配置项之间会互相抵消，理论账算对了不代表实测会对。**

### 6.6 FSDP1 的 flat param 要求 dtype 统一，LoRA 下必然冲突

LoRA 场景我让基座以 bf16 常驻，而 peft 新建的 adapter 默认是 fp32，
FSDP wrap 时报 `Must flatten tensors with uniform dtype but got torch.bfloat16 and torch.float32`。
把 adapter 也转成 bf16 才能跑。**代价是这一格的主权重变成 bf16，
与其它格（fp32 主权重）不是同一套精度口径**，已在 report 的局限里写明，
没有把它当作可直接横向比较的数字。

### 6.7 又一次把自己的 shell 杀掉（Day 08 同款）

临时命令里写 `pkill -f torchrun`，而同一条命令里有 `/root/.../bin/torchrun` 这个真实路径，
pkill 按 cmdline 匹配，把执行这条命令的 bash 也杀了（exit 127）。
换成 `pkill -f "[t]orchrun"` 也没用——括号技巧只在"模式本身是唯一一处出现"时有效，
而这里命令里另有真实的 torchrun 路径。
最后改成**把清理动作放到单独一次 SSH 调用里**。
（`run_day09.sh` 里的 `cleanup()` 是安全的：跑它的 bash 进程 cmdline 只有脚本路径。）

### 6.8 FSDP 的重叠系数重复性差

四次重复分别 1.79 / 1.10 / 1.19 / 1.41，极差 63%，而它的干净单步时间却很稳
（226.2 ms，block 间 std 0.3 ms）。说明抖动来自 profiler 观测本身，不是训练过程。
ZeRO-3 的两次则是 0.74 / 0.76，稳定。
**同一套观测手段对不同策略的稳定性可以差一个量级**，所以 report 里
FSDP 那一格给的是中位数 + 全部四个值，不用单次值下结论。
