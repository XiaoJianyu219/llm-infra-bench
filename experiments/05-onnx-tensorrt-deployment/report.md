# Day 05 — 从导出失败反查出静默失效,到 TensorRT 多档部署

## 0. 计划与实际

原计划:把一个自研小目标检测模型(YOLOv8n 主干 + 自研注意力模块,固定输入尺寸)
走 PyTorch -> ONNX -> TensorRT,测各档延迟与精度。

实际:第一步就导不出去。追查根因时发现模型里一个自研模块
**从未执行过它声称的计算**。主线变为:定位 -> 逐位证明 -> 等价简化 -> 导出 -> 部署。

## 1. 静默失效的定位

`torch.onnx.export`(dynamo)失败,trace 出现 unbacked SymInt:
`nonzero: "i64[u0, 2]"`、`gt_1: "Sym(u0 > 0)"`。

根因在该模块的 forward,形状推导与注释不符:

```python
pooled = pool(x, self.window_size)   # 注释声称输出 4 维
center = pooled[0, 0]                # 注释声称切出二维,实际切出一维
mask = center > 0.2
if mask.numel() == nH * nW:          # numel() 恒等于 nW,条件恒假
    mask = mask.view(nH, nW)
else:
    mask = zeros(nH, nW)             # 掩码被全零覆盖
if nonzero(mask).size(0) > 0:
    ...                              # 掩码窗口注意力
```

输入丢掉批维后,第一次池化看到的是三维张量,`pooled[0, 0]` 切出的是 **1 维**张量,
`numel()` 恒等于 `nW`。掩码恒被全零覆盖,注意力分支**一次都没执行过**。

### 三条独立证据

| # | 方法 | 结论 |
|---|------|------|
| 1 | dynamo trace 的逐行形状标注 | 池化输出实为 3 维,与注释不符 |
| 2 | 源码 `numel()` 谓词静态推导 | 条件左右两侧不等,恒假 |
| 3 | 运行时探针 | 执行掩码注意力的:**0/4** |

## 2. 等价简化

掩码分支不执行时,模块剩余的 pad/unfold/permute/view 完全逆向自身,
故 `module(x) == module.adapter(x)`。4 处模块替换为各自 adapter 后,
对 5 组输入比对完整模型输出:**最大绝对误差 0.000e+00,逐位恒等**。

| 指标 | 简化前 | 简化后 | 变化 |
|------|--------|--------|------|
| 参数量 | 100% | 65.14% | **-34.86%** |
| 精度 | — | — | **零损失(逐位恒等)** |

不是剪枝也不是蒸馏,没有任何近似:先证明一段计算对输出无贡献,再删除。
**三分之一的参数是死的。** 被删掉的大头是只服务于该分支的位置编码与投影矩阵,
不是几个小卷积——估模块开销要去数参数量,不要看名字猜。

## 3. 部署链路的版本耦合

TensorRT 11.3 移除了弱类型网络。实测 `BuilderFlag` 只剩
`TF32 / SPARSE_WEIGHTS / REFIT / ...` —— **FP16、INT8、BF16 全部不存在**;
`NetworkDefinitionCreationFlag` 里有 `STRONGLY_TYPED`。

含义:**精度不再由 builder flag 控制,必须由 ONNX 图自身携带类型**。
连带后果是基于 calibrator 的隐式 INT8 量化在 TRT 11 里已不可用,
INT8 必须走显式量化(图中插 QDQ 节点)。

上游 exporter 依次撞上 `EXPLICIT_BATCH`(已移除)和
`platform_has_fast_fp16`(已移除)。升级上游会冲掉以文件形式注册进包内的自研模块,
因此改为**绕开它,直接从 ONNX 自建引擎**:

- FP32:`create_network(0)` + OnnxParser
- FP16:先用 onnxconverter-common 把 ONNX 转 FP16(`keep_io_types=True`,
  保持 I/O 为 fp32 使接口不变),再用 `STRONGLY_TYPED` 构建

| | ONNX | 引擎 | 构建耗时 |
|---|---|---|---|
| FP32 | 12.5 MB | 262.4 MB | 99.8 s |
| FP16 | 6.3 MB | 189.4 MB | 116.1 s |

ONNX 正好减半,引擎只减 28% —— 引擎里除权重外还含 kernel 与 tactic,不成比例。

## 4. 三档对比(固定规模评测集,固定输入尺寸,batch=1,RTX 4090)

| 档位 | 中位延迟 ms | p99 ms | 相对 PyTorch |
|------|-------------|--------|--------------|
| PyTorch | 7.79 | 9.24 | 1.00x |
| TRT FP32 | 2.25 | 2.33 | **3.46x** |
| TRT FP16 | 1.21 | 1.25 | **6.41x** |

### FP32:与 PyTorch 实质等价

mAP50-95 与 mAP50 完全一致,逐类最大偏差 0.0005。
真实图像上 conf>0.25 的框:box 最大误差 **2.144e-02 px**,cls **1.447e-03**,
**类别翻转 0/190**。

### FP16:损失全部落在框的定位精度上

- mAP50 掉 0.0005,mAP50-95 掉 0.0049 —— **相差约十倍**
- 数值对齐:box 最大误差 **5.560e-01 px**,是 FP32 的 **26 倍**;
  cls 仅从 1.447e-03 涨到 3.284e-03,**类别翻转仍是 0/190**

两条独立证据指向同一机制:FP16 没有引入漏检或误分类,只是框位置抖动约半个像素。
半像素在 IoU 0.5 上无影响,在高 IoU 档位上直接体现为掉分。

### 脆弱的是难类,不是稀有类

逐类来看,降幅最大的类别约为最稳类别的十倍;而框数最少的类别反而最稳,
AP 最低的类别降幅最大。样本量不预测量化脆弱性。
(注:中间两类难度的降幅顺序并不随 AP 高低变化,故也不能简单说"AP 越低越脆弱"。)

## 5. 输入形状策略的代价远大于数值精度

为对齐固定形状引擎,评测统一改为 `rect=False`(强制方形)。同一模型在两种输入策略下,
mAP50-95 相差 **0.0379,是 FP16 量化损失(0.0049)的 7.7 倍**。

这条结论在 Day 06 被进一步核验:原先把差值归因于"按长宽比做矩形 letterbox"并不成立,
真实机制是另一种输入策略在有效图像四边各补了少量灰边;而且同样尺寸下固定形状引擎也能
复现这份收益,**动态形状并不是必要条件**。详见 Day 06 报告。

结论:对这类模型,**先把输入形状策略弄对,比在精度档位上纠结值钱得多**。

## 6. 测量纪律

PyTorch 的中位延迟在三轮里测出 8.09 / 6.45 / 7.79 ms,跨轮波动 25%;
标准差分别是 ±1.79 / ±0.09 / ±0.33。TRT 两档的标准差只有 ±0.06。

**标准差就是该轮数据可信度的自证。** 8.09 那轮是在引擎构建刚结束、
GPU 未冷却时测的,应当丢弃。

因此加速比只引用**同一次会话内**的配对数据。本报告第 4 节的
3.46x / 6.41x 来自同一轮。

另:TRT 默认流会触发额外的 `cudaStreamSynchronize`,已改为独立 CUDA stream
后重测,否则 TRT 侧延迟被系统性高估。

## 8. 可复用的方法

1. **导出失败是免费的静态分析。** 导出器要求静态形状,任何 data-dependent
   控制流都会被暴露。永远走同一分支的代码在 eager 下毫无征兆。
2. **先证明,再删除。** 0.000e+00 才是删除的许可证。
3. **数值误差要按置信度分层看。** 随机输入下 box 最大误差 1.546 px,
   真实图像高分框上只有 4.5e-03 px —— 相差 342 倍。
   全局最大误差被垃圾预测主导,会得出与部署结论相反的判断。
4. **精度损失要分解到指标的结构里。** mAP50 与 mAP50-95 的降幅之比,
   直接区分了"漏检/误分类"与"定位精度"两类损失。
5. **上游库落后于 CUDA 栈是常态。** 与其逐个打补丁追新版本 API,
   不如在稳定的中间表示(ONNX)处切断依赖,自建下游。
