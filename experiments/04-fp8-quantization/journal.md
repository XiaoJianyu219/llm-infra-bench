# Day 04 日志

## Day 4 · FP8 精确预测（压测前写入）

实测权重占用：bf16 16.65 GiB → FP8 10.18 GiB（比值 0.6114）

decode 受显存带宽支配（Day 1/2 已验证两次），故：
  预测 c1 TPOT = 17.2 ms × 0.6114 = 10.5 ms
  区间 10–12 ms（上界留给 FP8 反量化的额外开销）

  预测 c64 吞吐 = 3.57 → 6–8 req/s
  依据：带宽侧约 1.64×，容量侧 KV 池 +212%
  但 Day 2 显示容量增益次线性（KV +84% 仅换吞吐 +29%），故不做线性外推

  预测计数题准确率 81.5% → 掉点 < 5 个百分点，
  以 McNemar 配对检验判定显著性（独立比较在 n=200 下阈值高达 7.6 点，过钝）

若 c1 TPOT 落在 10–12 ms，则带宽模型第三次被验证，且首次是在
"改变权重精度"这个此前未测过的维度上——说明模型有外推能力而非拟合。

## Day 4 · 量化对照（bf16 vs FP8）

**环境**  新实例（第 5 台机器），RTX 4090。见 results/env/env-day04.txt

**做了什么**
- 本机重测 bf16 baseline，与 Day 1 的 4090 对照
- 构造 400 题合成评测集（颜色识别 200 + 计数 200），生成脚本入 repo，完全可复现
- 跑通 FP8 arm（官方权重 Qwen/Qwen3-VL-8B-Instruct-FP8）
- 精度用 McNemar 配对检验，而非直接比较准确率

**baseline 复现性**
四档吞吐 0.42 / 1.36 / 3.47 / 3.57，与 Day 1 的 4090 差异均在 1.4% 以内；
c1 TPOT 17.2 vs 17.3 ms。测量协议在同型号不同物理机上可复现。

**显存分配（固定 util 0.94，总占用几乎不变）**
                bf16          FP8         变化
  权重         16.65 GiB    10.18 GiB    −38.9%
  KV cache      3.05 GiB     9.52 GiB    +212%
  KV tokens     22,208       69,312      +212%
  max conc      2.71×        8.46×       +212%
  每 token KV   144 KiB      144.0 KiB   不变

**关键发现：FP8 只量化权重，KV cache 仍是 bf16。**
144 KiB/token 在两个 arm 下完全相同。要压 KV cache 需单独指定
--kv-cache-dtype fp8，这是独立的开关。此前误以为"FP8 模型"整体都是 FP8。

**表述修正**
"量化省了 38.9% 显存"不准确——两边总显存占用相同（均被 util 吃满）。
准确说法：量化在固定显存预算下，把资源从权重挪给 KV cache
（权重占比 75%→46%，KV 占比 14%→43%）。后者才解释得了吞吐为何提升。

**吞吐与延迟**  ← 待填
  c1 TPOT 预测 10.5 ms（区间 10–12），实测 ____
  c64 吞吐 3.57 → ____
  带宽侧增益 = 17.2 / 实测c1TPOT = ____
  容量侧贡献 = 总增益 / 带宽侧增益 = ____

**精度**
  bf16  90.75% ±2.84（颜色 100.0% / 计数 81.5%）
  FP8   89.50% ±3.00
  McNemar：b=6, c=1, χ²=2.29，不显著（p≈0.13）

结论：6:1 的分歧方向一致提示 FP8 略差，但仅 7 个分歧样本，
不足以在 α=0.05 下确认。保持该比例需约 12 个分歧样本才能过阈，
对应评测集需扩至约 700–800 题。

**局限**
- 合成评测集只覆盖颜色识别与计数，结论不可外推到 OCR、细粒度定位、复杂推理
- 颜色题 100% 满分无区分度，有效样本实为 200（计数题）
- AWQ-4bit arm 未跑，无 4bit 档位数据

## Day 4 · 量化对照（bf16 vs FP8）

**环境**  新实例，RTX 4090。见 results/env/env-day04.txt

**做了什么**
- 本机重测 bf16 baseline，与 Day 1 的 4090 四档吞吐差异均在 1.4% 以内
- 构造 400 题合成评测集（颜色 200 + 计数 200），生成脚本入 repo，可完整复现
- 跑通 FP8 arm（官方权重），压测 + 精度评测
- 精度用 McNemar 配对检验，非直接比较准确率

**关键数字**
- 权重 16.65 → 10.18 GiB，KV cache 3.05 → 9.52 GiB（+212%），
  KV tokens 22,208 → 69,312，max concurrency 2.71× → 8.46×
- 每 token KV 开销 144 KiB 在两 arm 下完全相同 → FP8 只量化权重
- 总显存占用几乎不变（均被 util 0.94 吃满），变的是分配比例
- 吞吐 c64：3.57 → 4.47（+25%）
- TTFT_p50 c1：248 → 131 ms（−47%）
- TPOT_p50 c1：17.2 → 17.8 ms（持平，差异在噪声内）
- TPOT_p50 c4/c16/c64：均降 17–18%
- 精度 90.75% → 89.50%，McNemar b=6 c=1 χ²=2.29，不显著

**预测失败**
预测 c1 TPOT = 17.2 × (10.18/16.65) = 10.5 ms，实测 17.8 ms。
带宽模型在"改变权重 dtype"这一维度上外推失败。

修正：vLLM 的 FP8 是 weight-only 量化，权重读取字节确实减少 39%，
但 GEMM 前需反量化，该开销纯计算、每步固定。
batch=1 时省下的 ~6.9 ms 带宽时间被 ~6–7 ms 反量化开销抵消；
batch≥4 后 Ada 原生 FP8 算力（约 1.7–2×）的收益超过该固定开销；
prefill 纯算力密集，完全吃到红利，故 TTFT 降 47%。

修正后模型：TPOT ≈ 权重字节/带宽 + 反量化开销 + batch 相关算力项。
bf16 的反量化项为零，故原模型此前一直成立。

**表述修正**
"量化省显存"不准确 —— 总占用不变，是把资源从权重挪给 KV cache。
"量化让 decode 变快"也不准确 —— batch=1 时完全没变快。

**吞吐增益分解**
带宽侧 = 17.2/17.8 = 0.97×，贡献为零。
+25% 全部来自 prefill 加速、KV 池扩大 3.1 倍、大 batch 算力优势。
与开工时的直觉完全相反。

**未解释**
FP8 的 TPOT 在 c1 (17.8) 高于 c4 (16.3)，与单调性矛盾，
8.4% 差异超噪声。疑与 CUDA graph capture size 有关，未查证。

**方法论收获**
- 预测失败比预测成功信息量大：它定位到了模型缺失的那一项，
  而三次成功只是重复确认已知。
- 精度比较必须用配对检验。n=200 下独立比较的显著阈值达 7.6 个点，
  会把真实的小差异全部判成噪声。
