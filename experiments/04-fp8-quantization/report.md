# Day 4 · FP8 量化：一次失败的预测，和一个被修正的模型

压测前基于带宽模型预测 FP8 的 c1 TPOT 为 10.5 ms（bf16 实测 17.2 ms）。
实测 17.8 ms，预测失败。本文说明模型缺了哪一项，以及修正后如何解释全部四档数据。

## 配置

两个 arm 除模型权重外参数完全相同，同一台机器连续测量。
bf16 baseline 在本机重测，与 Day 1 的 4090 四档吞吐差异均在 1.4% 以内。

```
Qwen/Qwen3-VL-8B-Instruct        （bf16）
Qwen/Qwen3-VL-8B-Instruct-FP8    （官方 FP8 权重）
max-model-len 8192 / gpu-memory-utilization 0.94 / max-num-seqs 16
负载：512 in / 128 out 合成多模态请求，每档 3 次取中位数
噪声底：低并发 3.1–4.2%，conc64 为 0.2%
```

## 显存分配

| | bf16 | FP8 | 变化 |
|---|---|---|---|
| 权重 | 16.65 GiB | 10.18 GiB | −38.9% |
| KV cache | 3.05 GiB | 9.52 GiB | +212% |
| KV tokens | 22,208 | 69,312 | +212% |
| max concurrency | 2.71× | 8.46× | +212% |
| 每 token KV | 144 KiB | 144.0 KiB | **不变** |
| 实测显存峰值 | 21,985 MiB | 22,041 MiB | 几乎相同 |

**结论 1：FP8 只量化权重，KV cache 仍是 bf16。**
每 token 的 KV 开销在两个 arm 下完全相同（144 KiB）。要压 KV cache
需单独指定 `--kv-cache-dtype fp8`，是独立的开关。

**结论 2：量化不是"省显存"，是在固定预算下重新分配显存。**
两边总占用几乎相同（均被 gpu-memory-utilization 0.94 吃满），
变的是分配比例：权重占比 75% → 46%，KV cache 占比 14% → 43%。
"省了 38.9% 显存"这个说法解释不了吞吐为何提升；
"把资源从权重挪给 KV cache"才能。

## 性能

| conc | req/s bf16→FP8 | TTFT_p50 | TPOT_p50 |
|---|---|---|---|
| 1 | 0.42 → 0.42 (0%) | 248 → 131 ms (**−47%**) | 17.2 → 17.8 ms (+3.5%) |
| 4 | 1.36 → 1.65 (+21%) | 419 → 346 ms | 19.7 → 16.3 ms (−17%) |
| 16 | 3.47 → 4.32 (+25%) | 911 → 638 ms | 27.4 → 22.5 ms (−18%) |
| 64 | 3.57 → 4.47 (+25%) | 13589 → 10765 ms | 31.6 → 25.9 ms (−18%) |

**结论 3：prefill 快 47%，batch=1 的 decode 完全没变快，batch≥4 的 decode 快 17–18%。**

c1 的 TPOT 差异 3.5% 落在该并发档 3.1–4.2% 的噪声底内，判定为持平。

## 预测的失败与模型的修正

**原预测**：decode 受权重读取带宽支配（Day 1/2 已两次验证），
权重 16.65 → 10.18 GiB，故 TPOT 应从 17.2 降至 10.5 ms。

**实测 17.8 ms，预测失败。**

**修正后的解释**：vLLM 的 FP8 为 weight-only 量化——权重以 FP8 存储
（读取字节确实减少 39%），但送入 GEMM 前需反量化。该开销是纯计算、
且每步固定，不随 batch 变化。

```
batch=1（带宽支配）
  节省的带宽时间 ≈ (16.65 − 10.18) GiB ÷ 1008 GB/s ≈ 6.9 ms
  反量化开销     ≈ 6–7 ms
  两者近似抵消 → TPOT 持平

batch≥4（转向算力支配）
  Ada 架构原生 FP8 算力约为 bf16 的 1.7–2×
  算力收益超过固定的反量化开销 → TPOT 降 17–18%

prefill（纯算力密集）
  完全吃到 FP8 算力红利 → TTFT 降 47%，约 1.9×
```

修正后的模型：

```
TPOT ≈ 权重字节 ÷ 带宽 + 反量化开销 + batch 相关算力项
```

bf16 的反量化项为零，故原模型在 bf16 上始终成立；引入 FP8 后缺失项暴露。
原模型在"改变 batch"（Day 2）与"改变硬件算力"（4090 vs 4090D）
两个维度上外推成功，在"改变权重 dtype"这一维度上失败。

## 吞吐增益的来源分解

```
带宽侧增益 = c1_TPOT_bf16 / c1_TPOT_FP8 = 17.2 / 17.8 = 0.97×
总增益（c64） = 4.47 / 3.57 = 1.25×
```

**带宽侧贡献为零。** +25% 的吞吐增益全部来自三处：
prefill 加速（1.9×）、KV 池子扩大 3.1 倍带来的并发能力、
以及大 batch 下 decode 的算力优势。

这与开工时的直觉（"权重小了读得快所以整体快"）完全相反。

## 精度

评测集：400 题合成选择题（颜色识别 200 + 计数 200），
生成脚本见 `scripts/make_synth_eval.py`，完全可复现。

| | 总体 | 颜色 | 计数 |
|---|---|---|---|
| bf16 | 90.75% ±2.84 | 100.0% | 81.5% |
| FP8 | 89.50% ±3.00 | — | — |

颜色题满分，无区分度；有效样本实为计数题的 200 条。

**McNemar 配对检验**：仅 bf16 对 6 题，仅 FP8 对 1 题，
χ² = 2.29 < 3.84，**不显著**（p ≈ 0.13）。

**结论 4：6:1 的分歧方向一致提示 FP8 略差，但 7 个分歧样本
不足以在 α=0.05 下确认。** 保持该比例需约 12 个分歧样本方能过阈，
对应评测集需扩至约 700–800 题。

采用配对检验而非独立比较，是因为后者在 n=200 下的显著阈值高达
7.6 个百分点（SE=2.75%），过于迟钝。

## 选型结论

在本配置下，FP8 相对 bf16：吞吐 +25%、首字延迟 −47%、
可服务并发上限 +212%，精度差异不显著。**推荐使用。**

但注意其收益结构与直觉相反——**若工作负载以单请求低并发为主
（batch≈1），FP8 的 decode 速度不会有任何改善**，收益仅体现在
prefill 与高并发场景。

## 局限与未解释项

- FP8 的 TPOT 在 c1 为 17.8 ms、c4 反降至 16.3 ms，与"TPOT 随 batch
  单调上升"矛盾，8.4% 的差异超出噪声。疑与 vLLM 的 CUDA graph
  capture size（[1,2,4,8,16,24,32]）有关，未查证。
- 反量化开销 6–7 ms 为由抵消关系反推所得，非直接测量。
  直接验证需 profiler 逐 kernel 计时。
- 合成评测集仅覆盖颜色识别与计数，结论不可外推至 OCR、
  细粒度定位、复杂推理等任务。
- AWQ-4bit arm 未跑，无 4bit 档位数据。
- 未测试 `--kv-cache-dtype fp8`，KV cache 仍有压缩空间未探索。
