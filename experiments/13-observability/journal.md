## 2. 写八股时才发现自己没想清楚的地方

这一节是本日最该保留的东西。按「缺口有多大」排序。

### 2.1 最大的缺口：**多模态的攒批我一次都没测过**

系统设计题一的第三节要回答「图像 token 数可变，怎么攒批」。我写的时候才意识到：

- **Day 03 是纯文本 LLM**（变长输出，连续批处理 vs 静态批处理，3.69×）；
- **Day 07 是纯视觉检测**（输入规范化后**定长**，每批一次前向就结束，**没有 token 级调度机会**）；
- **而多模态是两者的混合**：视觉编码段定长、语言解码段变长，**攒批策略要分段设计**。

**我手上没有任何一条实测覆盖这个混合体。** 我在稿子里能说的只有
「Day 03 的倍数不能直接套到视觉上」这个否定式，以及「按 token 数而不是请求数攒批」这个原则，
**但「按 token 攒批比按请求攒批好多少」我给不出数字。**

> 这是 Day 14 之后最该补的一项：**同一份多模态负载，按请求数攒批 vs 按 token 数攒批，
> 测吞吐与 p99 的差。** 它正好落在我的两个已有载体之间，补上以后题一就从"讲原则"变成"讲数字"。

### 2.2 PagedAttention：我测的是「问题有多大」，不是「方法有多好」

写 Q4 的时候卡住了一次。我有 KV cache 的单价（144 KiB/token，与理论逐字节吻合）、
有 GQA 的 4 倍收益、有「`Maximum concurrency` 2.71×→5.36× 是分母造成的账面变化」，
**但我没有任何一条「开分页 vs 关分页」的对照**——vLLM 里分页是默认且不可关的。

所以「PagedAttention 能提升多少」这个最常见的追问，**我只能答「我给不出这个数」**。
我最后把稿子改成：先讲机制，再讲**我实测到的那个浪费有多大**，最后明说没有对照实验。
**这个写法是诚实的，但它确实比有数字弱。**

> 可补的路子：不必去关 vLLM 的分页，而是**量化"最坏情况预留"这个假设本身**——
> 用同一份负载，比较「按 max_model_len 预留」与「按实际生成长度」的 KV 占用差，
> 这个能在不改 vLLM 的前提下算出来。

### 2.3 ZeRO 的显存对照其实不是单变量，我之前没把这点想透

Q2 我写「ZeRO-1 相对 DDP 省 41.8%」，写到边界那一段才想起 Day 09 报告里记过一条：
**DDP 走的是 fp32 参数 + autocast，DeepSpeed 走的是 bf16 参数 + fp32 主权重。
两者总账都是 16N，但组成不同**，autocast 还要额外缓存每个权重的 bf16 副本（2N = 1,137 MiB）。

**也就是说「省 41.8%」里混了一部分「精度组成差异」，不全是分片收益。**
Day 09 的局限一节已经写了这条，但我在写口述稿时**差点把它当成纯粹的分片收益讲出去**。

> 教训：**报告里写过的局限，转成口述稿时最容易被丢掉**——因为口述稿追求"一句话说清"，
> 而局限往往是第二句。**以后每条口述稿的"边界"部分，直接从报告的"局限"章抄。**

### 2.4 `6N` 的推导我会背，但推不严密

Q7 要当场推 `6N`。我能说「forward 2 倍参数量、backward 算两个梯度各 2 倍，合计 6 倍」，
**但被追问"为什么 backward 恰好是两个 2 倍而不是别的"时，我的说法是靠形状凑的，
不是从链式法则推的。** 严格讲：`dL/dx = dL/dy · Wᵀ` 和 `dL/dW = xᵀ · dL/dy`
这两个矩阵乘的 FLOPs 各自等于 forward 的 `xW`，因为三者都是同一组 `(in, out, tokens)` 的收缩。
**我把这句补进了稿子，但这是写的时候才补上的，原来讲不出来。**

### 2.5 千卡题里「超时该设多少」是我的判断，不是实测

我在稿子里给了「超时 ≈ 正常最长集合操作 × 5–10，并且训练步内与 checkpoint 分开设」。
**这条没有任何实测支撑**，我只有「正常抖动的量级」（保存 δ 极差是中位的 24%、最慢 3.5 倍）。
写的时候我直接标了"这是我的判断"。**但这类"看起来很专业的经验值"是最容易被追问穿的**，
所以我在追问库里专门放了一条让自己练。

### 2.6 AWQ 我只有一句话，且那句话我也不确定

Q6 的四个档位里，FP8/FP16/INT8 我都有自己的数，**AWQ 完全没有**（Day 04 明确记了"未跑"）。
我能说的只有"activation-aware 的 weight-only 4bit，按激活分布挑重要通道保护"。
**我做的一件有用的事是给出推论**：FP8 的 weight-only 在 batch=1 上因为反量化开销而完全没变快，
**4bit 的反量化开销只会更大，所以我预期它在 batch=1 上同样不会变快**——

## 3. 本日踩的坑

### 3.1 又犯了两个旧错（这一条单独写，因为用户点名过）

1. **`pkill -f 'dl.grafana.com'` 把我自己那条 SSH 命令一起杀了**，返回 `exit -1`。
   `-f` 匹配完整命令行，而我的命令字符串里就含有那个 pattern。
   **这是同一个错的第四次**（Day 08/09/10 各一次）。已写进长期记忆。
   **正确做法：清理进程写进独立 `.sh` 文件，或按 PID 杀，绝不在一行里同时出现 pattern 和 pkill。**
2. **`curl` 没关进度条，把两万多字符的进度条刷进了日志**，`tail -25` 拿回来全是回车行。
   **正确做法：远程下载一律 `--no-progress-meter`，日志只 grep 关键行。**

### 3.2 服务起不来：同名模块被 cwd 抢先解析

第一次启动服务报 `RuntimeError: Trying to create tensor with negative dimension -1: [-1, 3, 1024, 1024]`。

看起来像 TensorRT 动态 shape 的问题，实际不是：
`pipeline.py` 里写的是 `from trt_utils import TRTModel`，而我把 cwd 设成了 `/root/autodl-tmp/sod`，
那里有一份 **Day 05 留下的旧 `trt_utils.py`**，它在 `__init__` 里就按引擎声明的形状分配 buffer
（动态 batch 时那一维是 -1）；**Day 07 那版是惰性分配，第一次调用时才按实际 shape 分配。**
cwd 的优先级高于 `PYTHONPATH`，所以旧版赢了。

**按任务书第 8 节的排障顺序从第 1 层查，两分钟就定位到了**——
先 curl `/metrics` 拿不到 → 看服务日志 → 看 traceback 里的文件路径，
**路径本身就是答案**（`/root/autodl-tmp/sod/trt_utils.py` 而不是 `day07/scripts/trt_utils.py`）。

> 可复用的一条：**traceback 里的文件路径要逐个看，不要只看最后一行的异常类型。**

### 3.3 Prometheus 界面的时间参数按 UTC 解释

第一次构造带 `end_input=2026-09-19 00:01:30` 的 URL，界面显示 "Empty query result"。
服务器本地时间是 UTC+8，而 Prometheus 界面把那个时刻当成 UTC，指向了 8 小时后的未来。
改成「最近 30 分钟」（不指定结束时刻）就正常了；界面横轴显示的也确实是 UTC（15:54 而非 23:54）。

**这一条属于"面板截图里时间范围不对"那类坑**（任务书第 4 节第 4 条），
只是我撞到的是它的上游——查询本身就没数据。

### 3.4 Grafana 装不上

三个源实测 12 秒 0 字节（证据 `results/grafana_unreachable.txt`）。
**同一网络下 Prometheus 从 GitHub 下载是 3.4 MB/s，所以不是整体网络问题，
是 `dl.grafana.com` 这一个源不可达**，而 Grafana 官方不在 GitHub release 里放二进制。

处置与 Day 12「AutoDL 起不了 dockerd」同一套：**先判定、再如实标注、不伪造**。
dashboard JSON 照常交付并在文件头写明「未在 Grafana 中渲染过」，
截图改用同一批 PromQL 渲染并在图注标明。

### 3.5 任务书自己引用的两个数字与报告对不上

任务书 3.3 写「Day 07 实测单卡端到端 6.0 ms」「引擎层 6.41× 的加速端到端只剩 2.32×」。
回查 Day 07 报告：**端到端是 31.037 ms（fp16_gpu）/ 34.538 ms（fp16_cpu），
端到端加速是 1.12× 不是 2.32×**；6.41× 是 **Day 05 的纯推理段**（另一台机、800 张），
Day 07 同进程配对下引擎段是 **3.81×**。

**结论方向完全一致，而且实测比任务书的说法更极端。**
我按报告原始数字写，并在 `sd_inference.md` 开头列了对照表。
**这正是先做 facts.md 的价值——不先把数字集中起来，我会直接把 6.0 ms 抄进稿子。**
