## 0. 读这份索引前必须知道的四条口径

- **F0.1 三台机器，不可混比。** Day 01–08 与 Day 11 在 bjb1 的 4090 上；Day 09 在 bjb1 双卡 4090；
  Day 10 换到 bjb2 双卡 4090（GPU UUID 不同）。Day 10 换机后重测分母：all-reduce busbw
  15.30 → 12.37 GB/s（−19.2%），GEMM 峰值 155.57 → 169.04 TFLOPS（+8.7%），
  单卡 micro2 吞吐 7,436 → 6,029 tok/s（−18.9%）。**同一个配方在两台机器上的数不能相减。**
- **F0.2 两个载体，不可混比。** LLM 侧是 Qwen3-VL-8B（Day 01–04，vLLM 推理）与 Qwen3-0.6B
  （Day 08–11，训练）；视觉侧是自研小目标检测模型（YOLOv8n 主干，1024²，4 类，Day 05–07）。
- **F0.3 显存有三档口径，选哪档会改变结论。** `max_memory_allocated` / `max_memory_reserved` /
  `nvidia-smi`。[Day 08] 开 gradient checkpointing 后 allocated 降 28.0%，reserved 只降 6.7%，
  nvidia-smi 只降 6.5%。[Day 09] ZeRO-1 相对 DDP，allocated 降 41.8%，nvidia-smi 只降 19.3%。
  **用 nvidia-smi 衡量分片/重算的收益，会把 42% 看成 19%、把 28% 看成 6.5%。**
- **F0.4 噪声地板决定「多大算变化」。** [Day 10] 配置完全不变、独立进程重复 10 次，
  吞吐极差 **1.87%**（2σ 口径 0.98%）。[Day 02] conc16 噪声底 4.4–5.8%、conc64 0.1–0.7%。
  [Day 08] 不开 ckpt 进程间极差 0.42–0.64%，开 ckpt 劣化到 5.99–10.79%。

## 1. Day 01 — 推理性能基线（vLLM，Qwen3-VL-8B bf16，RTX 4090，512in/128out 多模态）

- [Day 01] 显存分解：权重 16.79 GiB（75.6%）、峰值激活 2.26 GiB（10.2%）、CUDA Graph 0.12 GiB（0.5%）、
  KV cache 3.05 GiB（13.7%），合计 22.22 GiB；启动时卡上可用 23.13 GiB。
- [Day 01] **权重被所有请求共享只占一份，KV cache 每请求独占一份**，所以并发上限由 KV cache 容量决定，与权重大小无关。
- [Day 01] KV cache 实测 3.05 GiB / 22,208 tokens = **144 KiB/token**；
  理论 `2(K,V) × 36 层 × 8 KV头 × 128 head_dim × 2 B = 147,456 B = 144 KiB`，**逐字节吻合**。
- [Day 01] GQA 收益可量化：该模型 32 个注意力头但只有 8 组 KV。若为标准 MHA（32 组 KV），
  每 token 开销 576 KiB，同样 3.05 GiB 只能装 **5,552 tokens**；**GQA 使可服务上下文提升 4 倍**。
- [Day 01] 并发扫描（req/s | TTFT_p50 | TPOT_p50）：
  conc1 0.42 | 229 ms | 17.3 ms；conc4 1.36 | 416 ms | 19.7 ms；
  conc16 3.45 | 844 ms | 28.5 ms；conc64 3.52 | **13,814 ms** | 32.4 ms。
- [Day 01] **吞吐在并发 16 附近饱和**：16→64 吞吐只涨 2%（3.45→3.52），而 TTFT_p50 涨 **16.4 倍**。
  饱和后加并发只延长排队，不增加有效产出。
- [Day 01] **瓶颈在排队而非生成**：TPOT 只从 17.3 涨到 32.4 ms（不足 2 倍），远小于 TTFT 的 16 倍。
- [Day 01] 单请求 decode 受显存带宽支配：conc1 TPOT 17.3 ms ≈ 权重读取时间 17.9 GB ÷ 1008 GB/s = **17.8 ms**。
  **此时算力大量闲置，这是批处理能近乎免费提升吞吐的原因。**
- [Day 01] **Little 定律交叉验证四档全部吻合在 4% 以内**（偏差 2.0% / 0.7% / 3.8% / 1.4%）：
  并发 ÷ 吞吐 ≈ TTFT + 127 × TPOT。四个指标不是各自独立测的，约束成立说明测量自洽。
- [Day 01] **nvidia-smi 观测不到 KV cache 真实使用量**：conc16 与 conc64 显存峰值完全相同（22,215 MiB），
  因为 vLLM 启动时一次性预分配整个池子。要看真实占用率必须读 `/metrics` 的 `gpu_cache_usage_perc`。

## 2. Day 02 — 服务参数对 KV cache 与吞吐的影响

- [Day 02] **每 token 的 KV 开销是模型结构常量**：五种池子配置下均为 144 KiB/token。
  调 `gpu-memory-utilization` 只改池子总量，不改单 token 开销。
- [Day 02] **限制并发吞吐的是 KV cache 容量，不是调度器上限**：
  KV tokens 15,088 → 27,712（+84%）对应 conc64 吞吐 3.10 → 4.00 req/s（+29%），单调无反常点；
  而 `max-num-seqs` 16→64 只带来 +8.4%，16→256 无进一步增益。
- [Day 02] 收益递减来自 roofline 位置移动：池子放大使有效 batch 增大，TPOT 从 29.7 升到 43.7 ms，
  故池子 +84% 只换来吞吐 +29%。
- [Day 02] 独立佐证（kvcache_demo）：prompt 312 token 下，有无 KV cache 的**前向 token 数差 58.6×，
  耗时只差 2.10×** —— GPU 处理 1 个 token 与 300 个 token 耗时接近，因为权重读取是固定成本。
- [Day 02] **缩小 max-model-len 不提升真实吞吐**：`len4096` 3.58 vs `seqs64` 3.60 req/s（噪声内），
  但启动日志的 `Maximum concurrency` 从 2.71× 跳到 5.36× —— **分母减半使其翻倍，是账面变化**。
  **读任何「最大并发」类指标前必须先确认它的分母。**
- [Day 02] 池子过小同时恶化尾延迟：`util90` 在 conc16 的 TTFT_p99 为 3,896 ms，
  约为其他配置（约 1,900 ms）的两倍，而 p50 只高 10% —— 指向偶发排队/抢占而非全局变慢。
- [Day 02] 零代码调参成果（conc64）：吞吐 3.32 → 4.00 req/s（**+20.5%**），
  TTFT_p50 14,560 → 9,391 ms（**−35.5%**），KV 容量 22,208 → 27,712 tokens（+24.8%）。
  主要来自显式指定 `--kv-cache-memory`，榨干 `gpu-memory-utilization` 未覆盖的剩余显存。

## 3. Day 03 — 连续批处理 vs 静态批处理（纯文本，200 请求，泊松 λ=4.0）

- [Day 03] **定长负载（128 token）加速比只有 1.17×**：continuous 3.82 vs static 3.27 req/s；
  但 p50 2.4 vs 9.3 s（**3.9×**）、p99 2.5 vs 14.3 s（**5.7×**）。
  **定长负载下代价体现为延迟而非吞吐；「加速比」只报吞吐会严重低估差距。**
- [Day 03] **变长负载（32–512 等概率）加速比 3.69×**：3.45 vs 0.94 req/s；
  p50 2.6 vs 92.8 s（**35.7×**）、p99 12.2 vs 165.4 s（13.6×）。
- [Day 03] **最刺眼的一条**：一个只要 32 个输出 token 的请求，静态批处理下等 **92.6 秒**，
  而它自身只需要 **0.6 秒** —— 被放大 **154 倍**。
- [Day 03] **连续批处理的延迟严格正比于请求自身长度**：0.6/32 = 1.2/64 = 2.4/128 = 4.8/256 = 9.6/512
  = **18.75 ms/token**，截距约为零。**每个请求只为自己要的东西付费。**
- [Day 03] **静态批处理的延迟与请求自身长度无关**：82–95 s 之间浮动 13%，无随 out_len 上升的趋势。
- [Day 03] **优势主要来自处理长度不均的能力，而非批处理本身**：1.17× 对 3.69×，相差 3.2 倍。
- [Day 03] 延迟爆炸是**过载的后果**不是批内等待本身：批内 max_new 取最大值 → 吞吐降到 0.94
  → 到达率 4.0 > 服务率 0.94，**系统过载 4.3 倍** → 队列无界增长。
  批时长本身只有 17 s，而中位延迟 92.8 s。
- [Day 03] 交叉验证一：批大小 16、5 个长度等概率，批内最大值为 512 的概率 `1−(4/5)^16 = 97.2%`，
  预测吞吐比 0.25，实测 0.94/3.27 = **0.287**。
- [Day 03] 交叉验证二：批时长 212.8 s ÷ 12.5 批 ≈ 17 s，第 100 个请求落在第 7 批，
  预测延迟 94 s，实测 out_len=128 组中位 **94.2 s**。

## 4. Day 04 — FP8 量化（Qwen3-VL-8B-Instruct-FP8，官方权重）

- [Day 04] **FP8 只量化权重，KV cache 仍是 bf16**：每 token KV 开销两个 arm 完全相同（144 KiB）。
  要压 KV 需单独指定 `--kv-cache-dtype fp8`，是独立开关。
- [Day 04] **量化不是「省显存」，是在固定预算下重新分配显存**：
  权重 16.65 → 10.18 GiB（−38.9%），KV cache 3.05 → 9.52 GiB（**+212%**），
  KV tokens 22,208 → 69,312，而**总占用几乎不变**（21,985 vs 22,041 MiB，都被 util 0.94 吃满）。
  权重占比 75% → 46%，KV 占比 14% → 43%。
- [Day 04] 性能：conc1 吞吐 **0%**、TTFT 248→131 ms（**−47%**）、TPOT 17.2→17.8 ms（+3.5%，落在噪声内）；
  conc64 吞吐 3.57→4.47（**+25%**）、TPOT 31.6→25.9 ms（−18%）。
- [Day 04] **预测失败并被修正的一条**：按带宽模型预测 FP8 的 c1 TPOT 应降到 10.5 ms，实测 17.8 ms。
  原因是 vLLM 的 FP8 是 **weight-only 量化**，送入 GEMM 前要反量化，该开销纯计算、每步固定、不随 batch 变化。
  batch=1 时节省的带宽时间（≈6.9 ms）与反量化开销（≈6–7 ms，**由抵消关系反推，非直接测量**）近似抵消。
- [Day 04] 增益来源分解：**带宽侧贡献为零**（17.2/17.8 = 0.97×）。+25% 全部来自
  prefill 加速（1.9×）、KV 池子扩大 3.1 倍带来的并发能力、大 batch 下 decode 的算力优势。
- [Day 04] **若负载以单请求低并发为主（batch≈1），FP8 的 decode 速度不会有任何改善。**
- [Day 04] 精度：400 题合成选择题，bf16 90.75% vs FP8 89.50%；
  **McNemar 配对检验 χ²=2.29 < 3.84，p≈0.13，不显著**（仅 bf16 对 6 题、仅 FP8 对 1 题）。
  保持 6:1 比例需约 12 个分歧样本才过阈，对应评测集要扩到 700–800 题。

## 5. Day 05 — TensorRT 三档部署 + 一次静默失效（自研检测模型，1024²，800 张）

- [Day 05] **一个自研模块从未执行过它声称的计算**：`pooled[0,0]` 切出 1 维使 `numel()` 恒等于 nW，
  掩码恒被全零覆盖，注意力分支运行时探针实测执行 **0/4** 次。
- [Day 05] 证明后删除：参数量 4,625,076 → 3,012,848（**−34.86%**），
  5 组输入下完整模型输出**最大绝对误差 0.000e+00，逐位恒等**。**三分之一的参数是死的。**
- [Day 05] **导出失败是免费的静态分析**：导出器要求静态形状，任何 data-dependent 控制流都会被暴露；
  永远走同一分支的代码在 eager 下毫无征兆。
- [Day 05] 三档对照（固定评测集）：PyTorch 中位 7.79 ms；TRT FP32 2.25 ms（**3.46×**）；
  TRT FP16 1.21 ms（**6.41×**）。FP32 与 PyTorch 精度实质性一致；FP16 的 mAP50 只降 0.0005。
- [Day 05] **输入形状策略的代价远大于数值精度**：两种输入策略的 mAP50-95 相差 0.0379，
  是 FP16 量化损失（0.0049）的 **7.7 倍**。（Day 06 核验后修正了原因归因：原"长宽比 letterbox"
  的解释不成立，真实机制是四边补灰边，且固定形状同样能复现收益。）
- [Day 05] **脆弱的是难类不是稀有类**：逐类相对降幅最大约 3%、最小约 0.3%；
  框数最少的类别反而最稳，AP 最低的类别降幅最大。**样本量不预测量化脆弱性。**
- [Day 05] 测量纪律：PyTorch 中位延迟三轮测出 8.09 / 6.45 / 7.79 ms（跨轮波动 25%），
  标准差 ±1.79 / ±0.09 / ±0.33；TRT 两档标准差只有 ±0.06。
  **标准差就是该轮数据可信度的自证**，8.09 那轮是引擎刚构建完、GPU 未冷却时测的，应当丢弃。
- [Day 05] 引擎体积：FP32 ONNX 12.5 MB → 引擎 262.4 MB；FP16 ONNX 6.3 MB → 引擎 189.4 MB。
  **ONNX 正好减半，引擎只减 28%** —— 引擎里除权重外还含 kernel 与 tactic。

## 6. Day 06 — INT8 显式量化与输入尺寸（eval600）

- [Day 06] **Day 05 的长宽比解释被自己推翻**：评测图片全部为正方形，原解释不成立；
  真实机制是另一种输入策略在有效图像四边各补了少量灰边，抽查中心像素差为 0。
- [Day 06] 同一评测集上换成带灰边的输入：mAP50-95 **+0.03965**；固定与动态两种引擎结果几乎相同
  （差 0.00004）——**动态形状不是这份收益的必要条件**；同尺寸下动态相对固定的中位延迟 -2.45%。
- [Day 06] **INT8 全量 QDQ 精度归零的根因是输出表示**：最终输出把像素坐标与概率拼在同一个张量，
  以 **scale=8.534** 做对称 INT8 量化，0–1 的概率全部落入零的舍入区间，类别分数整体失效。
- [Day 06] 排除输出头后精度可用，但仍**有超过六分之一的参考高分候选跌破阈值**（47 个从低分升过阈值），
  最大类别分数绝对误差 0.395 —— **argmax 未翻转不等于检测敏感度未变。**
- [Day 06] 同会话配对延迟（中位 ms）：PyTorch 5.329 / FP32 2.151 / FP16 1.254 / INT8 候选 1.694 /
  动态 FP32@1024 2.315 / 固定 FP32@1056 2.600。
- [Day 06] 背景图虚警（27 张，conf>0.25）：PyTorch1024 18 框 / 1056 32 框 / FP16 19 / INT8 候选 13 /
  INT8 全量 0。**INT8 全量的「零虚警」源于模型失效，不能解释成安全收益。**

## 7. Day 07 — 端到端服务化与动态批处理（新机重建引擎）

- [Day 07] **七段配对计时（fp16_cpu，中位 ms）**：decode 13.284 / preprocess **15.441** / h2d 1.393 /
  **inference 1.471** / d2h 0.490 / nms 2.279 / restore 0.105 / **端到端 34.538**。
- [Day 07] **引擎段加速 3.81×（5.601 → 1.471 ms），端到端只剩 1.12×（38.650 → 34.538 ms）。**
  引擎快出来的 4.1 ms 被 28.7 ms 的 CPU 解码+预处理淹没。
- [Day 07] **最大单段是 preprocess（15.441 ms）不是 NMS** —— 推翻了开工时的预测。
  **不能把 Day 05 计数器里的后处理时间直接认定为当前瓶颈。**
- [Day 07] GPU 后处理：端到端 34.538 → 31.037 ms（1.113×），NMS 段 2.279 → 0.980 ms。
- [Day 07] 并发扫描（batch上限1、wait0）：conc1 37.68 QPS / p99 34.81 ms；conc4 42.70 / 113.61；
  conc16 43.72 / 377.70；conc64 43.56 / **1492.50**。
  **吞吐从 conc16 到 conc64 基本不变（43.72→43.56），p99 涨 4 倍，主要代价是排队。**
- [Day 07] 全网格（192 次运行）观测最大 **43.93 QPS**（batch16/wait0/conc4，p99 117.28 ms），
  只比 42.70 高 2.86%，而该点三次重复峰谷差 4.39% —— **不足以宣称大 batch 更优**。
- [Day 07] **GPU 平均利用率只有 4–12.4%，峰值显存 2207–2977 MiB。**
  这个服务是 **CPU 前处理受限**，不是 GPU 受限。
- [Day 07] NMS 一致性：GPU 路线与 CPU 基线在全部评测图上**逐位相同**（100%，0 框数差异）；
- [Day 07] 视觉批处理与 LLM 批处理不同：视觉输入规范化后长度固定，每批一次前向即结束，
  **没有 token 级调度机会，不能把 Day 03 的倍数直接套用**。

## 8. Day 08 — 单卡训练 profiling（Qwen3-0.6B，RTX 4090）

- [Day 08] **MFU 28.40%（标准口径），含 lm_head 34.94%。** 两个都对，只是口径不同。
- [Day 08] **bound 判定用三条互不依赖的证据，全部指向 memory/overhead-bound：**
  E1 算子时间构成——GEMM 家族只占 CUDA 时间 **37.2%**，optimizer 28.8% + elementwise 26.2% +
  softmax 5.8% + reduction 1.9% = **62.8%**；
  E2 GEMM 内部效率——这些 GEMM 自身跑到 **140.5 TFLOPS = 实测峰值 155.57 的 90.3%**；
  E3 batch 缩放（不用 profiler）——`step_ms = 114.3 + 19.7 × batch`，b=4 时固定开销占单步 **64.4%**。
- [Day 08] **「算力没吃满」是误读**：真正做矩阵乘的 kernel 已经跑到峰值的 90.3%，它们只占 37.2% 的时间。
  剩下 62.8% 的活算术强度远在 ridge point 之下，**加算力不会变快**。
- [Day 08] 排除 CPU 下发跟不上：profiler 记到 CUDA self time 181.9 ms/步，干净单步 187.8 ms，
  **空泡 ≤ 3.1%**；每步 5,506 次 kernel launch，GPU 始终是满的。
- [Day 08] 实测分母（不抄规格书）：bf16 GEMM 峰值 **155.57 TFLOPS**（规格 165.2 的 **94.2%**）；
  fp32 48.07（规格 82.6 的 58.2%，因 TF32 关闭，是真 fp32 CUDA core）；
  显存带宽 **948.4 GB/s**（规格 1008 的 94.1%）。**ridge point = 164.0 FLOP/byte。**
- [Day 08] **FLOPs 手推**：线性层每 token fwd 2×参数量、bwd dgrad 2×、bwd wgrad 2× → 合计 **6N**；
  attention 两个 batched matmul 不含参数，单列 `12·L·d_attn·s`。
- [Day 08] **一个会静默出错的地方**：`d_attn = num_heads × head_dim = 16 × 128 = 2048`，
  而 `hidden_size` 只有 **1024**，**两者差 2 倍**，代 h=1024 会把 attention 项低估一半。
- [Day 08] 每 token FLOPs：s=512 时 6N 2.643G + attention 0.352G = 2.995G（attention 占 11.8%）；
  s=2048 时 2.643G + 1.409G = 4.052G（attention 占 **34.8%**）。lm_head 另有 0.933G/token。
- [Day 08] **标准「6N 非 embedding」口径系统性低估约 23%**：`tie_word_embeddings=true` 使 lm_head
  被排除在 N 之外，但它是货真价实的 `[tokens, 1024] × [1024, 151936]` 矩阵乘，
  占总计算量 18.7%（s=2048）到 23.8%（s=512）。
- [Day 08] **MFU 与 HFU 的区别**：开 gradient checkpointing 后硬件多跑一次 forward，
  `HFU/MFU = 4/3 = 1.3333`；实测 MFU 22.51%、HFU 30.01%、比值 1.333。
  **只看 HFU 会觉得「硬件利用率从 28.4% 提到 30.0% 是改进」，而实际产出的 token 少了 20.7%。
  HFU 衡量硬件忙不忙，MFU 衡量有没有产出，选配置只能看 MFU。**
- [Day 08] bf16 AMP 对 fp32：吞吐 4,875 → 9,909 tok/s（**2.03×**），显存 18,345 → 16,645 MiB（**只省 9.3%**）。
  **AMP 只省 9.3% 显存**，因为参数+梯度+AdamW 两个 state 全是 fp32 共 **9.09 GB，与精度无关**；
  autocast 只把激活和中间张量变 bf16。
- [Day 08] gradient checkpointing：吞吐 10,903 → 8,642 tok/s（−20.7%），alloc 16,645 → 11,982 MiB（−28.0%）。
  **真正的收益不是省这 28%，而是把 OOM 墙从 4,096 token/步推到 12,288。**
  但推完并没有更快：能跑的最大配置 b12+ckpt 是 11,022 tok/s，**反而低于**不开 ckpt 的 b6 的 12,591 tok/s。
- [Day 08] flash SDPA 对 math（s512 b4）：吞吐 8,966 → 11,539 tok/s（+28.7%），显存 19,328 → 16,644 MiB（−13.9%），
  **同时更快更省**；s=2048 时 math 直接 OOM。math 的 softmax launch 从 6 次/3步 暴涨到 **174 次**。
- [Day 08] **「指定了不等于生效」**：指定 `cudnn` 后端实际跑的是 flash kernel（kernel 名、显存、吞吐全一致）。
  验证后端身份必须读 profiler 里真实出现的 kernel 名。
- [Day 08] **24 GB 上的硬约束：能不能跑起来只取决于每步 token 总数，与 batch/seq 怎么拆无关。**
  2,048 token 的四种 (s,b) 拆法显存差 **2 MiB**（16,643–16,645）；4,096 token 的三种拆法全部 OOM（22,946–22,947）。
  主导项是 lm_head 输出 `logits [tokens, 151936]`：bf16 tokens×0.29 MB，交叉熵内部 upcast 到 fp32 tokens×0.58 MB，
  加 log_softmax 保存与反传梯度各一份，4,096 token 时这一族约 9.5 GB。
- [Day 08] Pareto 膝点在 **16.29 GiB / 11,623 tok/s**：11.6 → 16.3 GiB 多花 4.7 GiB 换吞吐 **3.4 倍**；
  16.3 → 21.3 GiB 再花 5.0 GiB 只换 **8.3%**。
- [Day 08] 同样 2,048 token/步下，s=2048 与 s=512 吞吐只差 5.5%（10,903 vs 11,539）——**想要长上下文几乎是免费的**。
- [Day 08] 冷启动只有第 0 步异常（1595.2 ms vs 稳态 187 ms，8.5 倍），第 1 步起就稳态（±0.3%）。
- [Day 08] CNN 对照（YOLOv8n-det 1024² b4）：**optimizer 占比 28.8% vs 0.26%，差 110 倍**；
  kernel 种类 68 vs 102，但每步 launch **5,506 vs 1,534**（transformer 反而多 3.6 倍）。
  **「transformer 训练更 compute-bound」是错的说法**；真正的区分是「参数量大的模型，
  优化器本身就是一个 memory-bound 的大头」。

## 9. Day 09 — 双卡 DDP / ZeRO / FSDP（2×4090，无 NVLink）

- [Day 09] **硬件事实先确认不采信**，三条独立证据：`can_device_access_peer(0,1) = False`；
  NCCL 日志 `Channel 00 : 0[0] -> 1[1] via SHM/direct`、`isAllDirectP2p 0`；
  `nvidia-smi topo -m` 显示 GPU0↔GPU1 为 **NODE**（跨 PCIe Host Bridge）。
  **每个字节都要先从 GPU 写进主机内存，再从主机内存读回另一张卡。**
- [Day 09] **all-reduce busbw @1 GB = 15.30 GB/s**（NCCL 自估拓扑带宽 20 GB/s 的 76%）；
  @16 MB 14.61；@1 MB 10.67（延迟主导）。all-gather @1GB 12.69；reduce-scatter 12.72。
- [Day 09] **卡内 D2D 920.0 GB/s，卡间比卡内慢 60 倍。** 后面所有扩展效率归因都回到这一行。
- [Day 09] PCIe：H2D pinned 25.1 / D2H pinned 26.3 / H2D pageable 19.1 / D2H pageable 15.2 GB/s。
- [Day 09] busbw 换算：`algbw = S/t`，all-reduce `busbw = algbw × 2(P−1)/P`，
  all-gather / reduce-scatter 是 `× (P−1)/P`。**P=2 时 all-reduce 系数恰好为 1，这一档没有区分度，
  要 P≥4 才拉开；两种系数不能混用。**
- [Day 09] 显存理论账（N=596,049,920，混合精度 AdamW 每参数 16 字节 = bf16参数2 + bf16梯度2 + fp32主权重4 + m4 + v4）：
  DDP 16N；ZeRO-1 切优化器状态 12N → 12N/P + 4N = 10N；ZeRO-2 再切梯度 → 9N；
  ZeRO-3 / FSDP 再切参数 → 16N/P = 8N。
- [Day 09] 理论 vs 实测 alloc（MiB）：DDP 9,094 / 14,286；ZeRO-1 5,684 / 8,318；ZeRO-2 5,116 / 8,318；
  ZeRO-3 4,547 / **9,627**；FSDP 4,547 / **7,509**。
- [Day 09] **差额的三个来源**：① 激活与 logits 约 2,900–3,200 MiB，**不被任何 ZeRO stage 切分**；
  ② DDP 多出约 2,200 MiB 是精度组成不同（autocast 要为每个权重缓存 bf16 副本，额外 2N=1,137 MiB）；
  ③ ZeRO-3 的 +5,080 MiB 是 all-gather 临时缓冲——**在 0.6B 这个规模上缓冲区吃掉的比分片省下的还多**。
- [Day 09] **ZeRO-1 与 ZeRO-2 实测显存完全相同（都是 8,318 MiB）**，因为 `contiguous_gradients: true`
  会预留一整块连续梯度缓冲，理论上该省的 2N/P = 568 MiB 没省下来。
- [Day 09] 吞吐与扩展效率（weak）：单卡 micro2 7,436 tok/s（基准）；DDP 7,671（**51.6%**）；
  ZeRO-1 7,745（52.1%）；ZeRO-2 8,535（57.4%）；**ZeRO-3 3,968（26.7%）**；**FSDP 9,056（60.9%）**。
- [Day 09] **FSDP 比 ZeRO-3 快 2.28 倍，而两者切的张量与通信量几乎相同（都约 3.6 GB/步）。
  差别不在算法，在通信有没有被藏起来**：重叠系数 FSDP 1.19 vs ZeRO-3 **0.76**（GPU 真实空泡 23.8%）。
  ZeRO-3 的通信 kernel 启动 405 次 vs FSDP 258 次，粒度更碎、更难摊薄延迟。
- [Day 09] **用实测带宽做的交叉验证**：DDP 每步 all-reduce fp32 梯度 `4 × 596,049,920 = 2.384 GB`，
  按 15.30 GB/s 预测 155.8 ms，profiler 实测 NCCL kernel 169.4 ms/步，**偏差 8.7%**。
  两个互相独立的测量吻合在 9% 以内。
- [Day 09] 单卡 137.7 ms + 通信 169.4 ms = 307.1 ms（完全暴露），实测单步 267.0 ms，**藏进计算约 40 ms**。
- [Day 09] **LoRA 下整张表塌掉**（可训练 4,587,520 / 600,637,440 = **0.764%**）：
  DDP weak 效率 **84.6%**（全量微调只有 51.6%），因为梯度只有 4.6M×4B = 18 MB，**比全量的 2.38 GB 小 130 倍**；
  ZeRO-1/2 只省 5.7% 显存；**ZeRO-3 反而多用 14.4% 显存，吞吐只有 DDP 的 21%**。
  **在这台机器上做 LoRA，正确答案是最朴素的 DDP。**
- [Day 09] 选型：全量微调选 FSDP FULL_SHARD（同时拿下最高吞吐与最低显存，比 DDP 快 18%、省 47%）；
  **任何场景都不要在这台机器上用 ZeRO-3**。
- [Day 09] **更根本的结论：双卡在这台机器上对全量微调几乎不值得** —— 最好的 FSDP 也只有 60.9% 的 weak 效率，
  **付出两倍的卡换来 1.22 倍的吞吐**。双卡的真正价值是**放得下原本放不下的东西**（每卡 12.0 GB → 7.5 GB）。
- [Day 09] NVLink 外推（**外推非实测**，900 GB/s 是规格值）：四种策略吞吐会收敛到彼此相差几个百分点，
  选择依据从「谁的通信藏得住」变成「谁的显存省得多」。**文献里 ZeRO-3 吞吐损失常报个位数百分比，
  那些数字是在 NVLink/InfiniBand 上测的，搬到消费卡机器上会错得离谱。**

## 10. Day 10 — 通信优化与归因拆解（换机 bjb2）

- [Day 10] **aggregate MFU 5.85% → 31.82%（5.44×）**。拆开：单卡 MFU 10.68% → 36.85%（×3.451），
  扩展效率 54.8% → 86.4%（×1.577）。**取对数分账（顺序无关）：单卡侧 73.1%、通信侧 26.9%。**
- [Day 10] 拆解能成立是因为 `aggregate MFU = 单卡 MFU × 扩展效率`（10.68%×54.8%=5.85% ✓，36.85%×86.4%=31.82% ✓）。
- [Day 10] **aggregate 而不是 per-GPU 口径**：分母乘卡数，单卡与双卡可直接比较；
  用 per-GPU 口径双卡数字会凭空翻倍，**那是记账错误**。
- [Day 10] **噪声地板 1.87%**（独立进程 10 次的吞吐极差，2σ 口径 0.98%）。
  所有 |Δ吞吐| < 1.87% 一律判为「不构成结论」。
- [Day 10] 有效的改动：梯度累积 k=2/4/8/16 → **+39.0% / +66.9% / +89.8% / +97.9%**；
  micro batch 4 → **+88.1%**；`NCCL_MIN_NCHANNELS=8` → **+15.4%**；`NCCL_NTHREADS=512` → +10.2%；
  fused AdamW → +12.0%；`torch.compile` → +8.2%（k=1）但叠在 mb4+k8 上值 **+45.9%**；
  `set_to_none=True` → +2.3%。
- [Day 10] **MIN 与 MAX 的区别是本日最有价值的一条 NCCL 结论**：
  `NCCL_MAX_NCHANNELS=8` 只抬高上限，NCCL 依旧按拓扑选 2 个 channel，**+0.2%（玄学）**；
  `NCCL_MIN_NCHANNELS=8` 是**强制**用 8 个，+15.4%。细扫：2→4 已兑现 +13.6%，8 饱和，16 反降。
- [Day 10] **`NCCL_PROTO=LL128` −21.1%（有效但有害）**：LL/LL128 用冗余标志位换低延迟、为小消息设计，
  这里 bucket 是 25 MB 级、带宽已饱和，加标志位只会变慢。
  **「对小消息有效」的旋钮用在大消息上不是无效而是有害。**
- [Day 10] `NCCL_SHM_DISABLE=1` → **−71.2%**（掉到基线的 28.8%），**反向验证了 Day 09 的 transport 判定**。
- [Day 10] **玄学清单**：扫了 10 个 NCCL 设置，2 个有效提速、2 个有效减速、**6 个低于噪声地板**；
  另扫 5 档 `bucket_cap_mb` 与 3 个 DDP 开关（`static_graph`、`find_unused_parameters`、
  `gradient_as_bucket_view`），**8 个全部低于噪声地板**。
- [Day 10] `bucket_cap_mb` 怎么调都没用的原因（实测而非猜测）：从 chrome trace 取通信 kernel 相对启动时刻，
  p25/p50/p75 = **0.19/0.48/0.78**，**bucket 确实在 backward 过程中分批触发、均匀散布，没有堆在最后**。
  调度已经是对的，瓶颈不在调度——通信时间 215.3 ms 本身就大于可藏的 backward 窗口。
- [Day 10] **交互作用：百分比不能相加。** A=k8（+86.8%）、B=mb4（+88.0%），
  A+B 实测 **+265.1%**，可加假设只有 +174.8%，**超可加 +90.3 pp**。
  机制：每优化器步通信量恒为 4N=2.38 GB 与 batch 无关，A 放大 8 倍、B 放大 2 倍，**A+B 放大 16 倍，倍数是相乘的**。
- [Day 10] 第二组交互方向相反：A=k8 与 C=MIN_NCHANNELS 都在通信侧，A+C 实测 +96.5% < 可加 +103.2%，
  **次可加 −6.7 pp**。**同侧两项互相挤占，跨侧两项互相放大——这就是拆解必须做实验而不能算术相加的理由。**
- [Day 10] **梯度累积把通信瓶颈换成了 kernel launch 瓶颈**：k=8 重叠系数 0.64、GPU 真实空泡 36.1%；
  k=8 每优化器步要发 **46,325 次 kernel**（k=1 只有 5,879），按约 10 µs/次推 ≈ 463 ms，
  **实测空档 471 ms，吻合**。这解释了 k=16 相对 k=8 只多涨 8 个百分点。
- [Day 10] 最终配置 `micro_bsz=4, grad_accum=8, NCCL_MIN_NCHANNELS=8, torch.compile`：
  双卡 **35,923 tok/s**，aggregate MFU 31.82%，显存 17,288 MiB/卡。
- [Day 10] 一条真实取舍：fused AdamW 单独测 +12.0% 有效，但叠到 mb4+k8 的显存水位上会 **OOM**——
  它需要额外的连续缓冲。
- [Day 10] TF32 on/off 都是 +0.6%（玄学），可以事先推出来：训练走 bf16 autocast，
  矩阵乘已在 bf16 tensor core 上，TF32 只影响未被 autocast 覆盖的 fp32 算子。
- [Day 10] NVLink 外推（**外推非实测**）：通信侧全部改动的价值从 27% 掉到约 2%，分账从 73:27 变成约 98:2；
  梯度累积在 NVLink 上不应再被当作性能手段。**同一个配方在两台机器上价值差 70 倍。**

## 11. Day 11 — 容错与断点续训

- [Day 11] **checkpoint 体积 7.15 GB**：模型权重 fp32 **2.38 GB（33.3%）**、优化器状态（AdamW m、v）
  **4.77 GB（66.7%）**，其余所有「小状态」（数据位置 128 B、RNG+scheduler+配置约 14 KB）
  合计约 14 KB，占 **0.0002%**。**「checkpoint 太大」的答案是优化器，不是模型，它是模型本身的两倍。**
- [Day 11] **先要可复现，判据才成立**：默认设置下不中断连跑两次，第 1 步起就分叉，最大绝对差 **2.962e-3**；
  `use_deterministic_algorithms(True, warn_only=True)` 仍不一致（1.02e-2，**只打告警不切实现**）；
  `warn_only=False` + `CUBLAS_WORKSPACE_CONFIG=:4096:8` 才**逐位一致（0.0）**，代价 **+2.4% 步时**。
  非确定来源是 **Flash Attention 的 backward 默认非确定**。
- [Day 11] **三档 checkpoint 完整度的恢复误差**：
  c0（权重+优化器）首步差 **2.911**、最大 3.149；
  c1（+数据位置+global step）首步 **4.12e-2** 但**越漂越大**（最大 1.165）；
  c2（+RNG+scheduler+配置）**全部 0.0，逐位一致**。
- [Day 11] **症状与病因的对应**：c0 首步就差很多 = **数据顺序没恢复**（sampler 从头来，重喂已训过的 batch）；
  c1「首步很小、之后单调变大」= **LR scheduler 没恢复**（预热从头开始，偏差随步数累积）。
- [Day 11] **最容易漏的状态**：数据加载位置、每个 rank 各自的 RNG、优化器 step 计数、LR scheduler。
  实测只存 rank 0 的 RNG 时，rank 1 恢复后 loss 11.271402 vs 掉卡前 11.316912，**对不上**；
  每个 rank 另存 RNG 旁路文件后两个 rank 都逐位对齐。
- [Day 11] **单次保存 δ = 5.923 s 中位**（范围 5.776–7.217），7.15 GB，折合单写者 **1.21 GB/s**。
- [Day 11] **Young/Daly 的 δ 常数假设有实测边界**：保存间隔 2 步时实测 δ 被拉长到 **14.52 s**（2.5 倍，最长 20.49 s），
  实测开销 **539%** 而常数 δ 预测只有 231%；间隔 16 步时 δ 回到孤立测量值，与公式吻合到 0.6 个百分点。
  **间隔短于「写完一次所需时间」的几倍时，公式不成立。**
- [Day 11] **推导**：`T(τ) = τ + δ + (τ+δ)/M · (τ/2 + R)`，一阶开销率 `H(τ) ≈ δ/τ + τ/(2M)`，
  求导得 **τ_opt = √(2δM)**，最小开销 **√(2δ/M)**，此时保存开销与重算损失各占一半。
  Daly 高阶修正 `τ = √(2δM)[1 + √(δ/2M)/3 + (δ/2M)/9] − δ`。
- [Day 11] 代入 δ=5.923 s：MTBF 1 小时 → τ_opt 207 s / 开销 5.74%；
  **MTBF 1 天 → τ_opt 1,012 s（约 794–1,284 步）/ 开销 1.17%**；MTBF 1 周 → 2,677 s / 0.44%。
  Daly 修正只差 4 秒，一阶够用。**每 10 步存一次会让吞吐降到约 68%。**
- [Day 11] **「掉一张卡」有两种相差三个数量级的故障**：
  ① `kill -9`（进程消失）→ torchrun 的 elastic agent **0.47 秒**内把整组拉掉，**NCCL 超时根本没被触发**；
  ② `SIGSTOP`（进程活着但不响应）→ 另一 rank 卡在 all-reduce，**等满集合超时（默认 600 s）再加约 92 s 尾巴**，
  即**约 11.5 分钟**才被发现。
- [Day 11] 超时由 `init_process_group(timeout=)` 精确控制（30 s / 60 s 实测误差 < 0.1 s）；
  **`TORCH_NCCL_TIMEOUT_MS` 这个环境变量不存在**（`libtorch_cuda.so` 里 24 个 `TORCH_NCCL_*` 变量中没有它）。
- [Day 11] `TORCH_NCCL_ASYNC_ERROR_HANDLING=0` 在 kill -9 下时间线完全相同——**这个开关在这种故障下不起作用**。
- [Day 11] 弹性重启实测：**第一次重启失败在 DDP 构造的 `_verify_params_across_processes`（一个集合操作），
  约 67 s 后才退出**，第二次才成功。**`--max-restarts` 至少要留 2 次。**
- [Day 11] 千卡外推（**含外部假设**：单卡 MTBF 取 Llama 3 报告量级、共享存储 100 GB/s、70B 模型 1.12 TB）：
  1,024 卡 MTBF 2.1 天 / τ_opt 33 min / 开销 1.12%；
  **16,384 卡 MTBF 3.1 h / τ_opt 8.3 min / 开销 4.49%**；100,000 卡 MTBF 30 min / τ_opt 3.4 min / 开销 **11.08%**。
  开销按 √N 增长，**最小开销到 10% 的临界规模约 8.1 万卡**。
- [Day 11] **存储先饱和**：每 rank 并行写分片时 δ = 总量/(N×1.21 GB/s)，
  共享存储 100 GB/s 在 **N ≈ 83 个并发写者**时饱和，此后 δ 固定在 11.2 s，
  **再加卡不会让保存变快，只会让故障更频繁**。
- [Day 11] 全局同步 checkpoint 贵在**掉队者**：同步本身不贵（1 MB all-reduce 0.110 ms），
  但 5 次孤立保存的 δ 极差 1.44 s（中位的 24%），频繁保存时最慢一次是中位的 **3.5 倍**；
  **同步保存的耗时是所有 rank 里最慢的那个，N 越大越接近尾部而不是中位数。**
- [Day 11] 异步快照（**推算非实测**）：按 D2H 26.3 GB/s，7.15 GB 的阻塞从 5.92 s 降到约 **0.27 s（22 倍）**，
  最小开销降为原来的 21%。**它解决 7.1 的故障率放大，解决不了 7.2 的存储饱和**（字节总量不变）。

## 12. Day 12 — 容器化与 Kubernetes 调度（本机 WSL2 + Docker + kind，无 GPU 节点）

- [Day 12] 镜像体积（`docker images` 未压缩口径）：`python:3.12-slim` 基座 **190 MB**；
  单阶段+留 pip 缓存 **555 MB**；单阶段+`--no-cache-dir` **447 MB**；多阶段 **434 MB**；
  多阶段+`apt install curl`+`RUN chown -R` **452 MB**（**反而更大**）。
- [Day 12] **多阶段的收益只有 13 MB / 2.9%**（447→434）：本日依赖全是预编译 wheel，没有编译工具链可丢。
  **多阶段的收益不取决于用不用多阶段，取决于镜像里有没有「只在构建期有用」的东西。**
- [Day 12] 两个「看起来很专业」的动作净增 18 MB：`apt install curl` 是纯负担（`httpGet` 探针由
  **kubelet 从节点发起，根本不进容器**）；`RUN chown -R` 会复制一整层（overlayfs 改属主=写新文件），
  正确写法是 `COPY --chown`。
- [Day 12] **体积有三个互不相等的口径**：`docker images` / `docker history` 各层求和 / registry 压缩。
  实测 190 vs 142.1、555 vs 392.2、447 vs 337.2、434 vs 327.1 MB；
  连差值都对不上（`docker images` 说 pip 缓存值 108 MB，`docker history` 说只差 55 MB）。
  同一个 `python:3.12-slim` 压缩 44 MB / 未压缩 190 MB = **4.3 倍**。**报体积必须报口径。**
- [Day 12] `.dockerignore` 补上 `bin/` 后 build context 从 **72.98 MB → 26.11 kB**（约 2800 倍）。
- [Day 12] **失败场景一（liveness 打 `/readyz` + 不配 startupProbe + 加载 90 s）**：
  `Liveness probe failed: HTTP probe failed with statuscode: 503` ×21 → `Killing` ×6 →
  `CrashLoopBackOff`，重启计数 7。容器每次只活约 20 s 而模型需要 90 s。
  **`lastState` 是 `exitCode 0 / reason Completed`（kubelet 发 SIGTERM，进程优雅退出），
  所以查日志找崩溃原因会一无所获——这类问题只能从 Events 看出来。**
- [Day 12] **失败场景二不需要故意做坏配置，它在正确配置下自己出现**：三探针分工清楚、
  liveness 只打极轻量的 `/healthz`，并发 8 压测下 4 个 Pod 各重启 3–4 次，全部是 liveness 杀。
  直接证据：**同一个 `/healthz` 空载 2–12 ms，压测中最高 5378 ms（约 2700 倍）**，远超 `timeoutSeconds: 2`。
- [Day 12] 根因在应用代码不在 YAML：`/predict` 写成 `async def`，FastAPI 对 `async def` 处理函数
  **直接在事件循环线程里执行**，而 `onnxruntime.run()` 是同步阻塞的 C++ 调用（1.5–4 s），
  这段时间整个 uvicorn 事件循环停转。
  **探针的轻重由整个进程的调度决定，不由这个 handler 自己决定。**
- [Day 12] **修好阻塞，故障没消失只是换了出口**：改成同步 `def` 后 liveness 失败事件 **0**，
  但四个 Pod 全部 **`exitCode 137 / OOMKilled`**，成功 27 / 失败 5405，**比修复前（210 / 45）差一个数量级**。
  `async def` 版本事实上充当了限流器（一个 Pod 同时只跑一次推理）。
- [Day 12] **容量标定（cgroup v2 `memory.peak`）**：峰值内存 ≈ **233 + 262 × 并发 MiB**
  （并发 8 预测 2329、实测 2355，误差 1.1%）；空载（模型已加载、无请求）只有 **90 MiB**——
  **第一次推理才会把 ORT arena 撑起来，只看「服务刚起来的内存」会严重低估**。
  由此 `limits.memory: 1Gi` 反推可承受并发 = (1024−233)/262 ≈ **3.0**，**并发 8 下 OOM 是算得出来的必然**。
- [Day 12] **CPU 利用率是错的扩容指标，有直接实验证据**：单副本、并发 1→16（负载涨 16 倍），
  `inflight` 1→21（涨 21 倍）、p50 1.94 s→22.36 s（涨 11 倍）、吞吐 0.48→0.25（**反而掉一半**），
  而 **CPU 利用率 390%→398%，变化在噪声里**。**HPA 在整个过程中看到的是一个常数。**
- [Day 12] **`averageUtilization` 的分母是 `requests` 不是核数，封顶值是 `limits/requests`**：
  本例 `2 / 0.5 = 400%`，不是 100%。**同一份 HPA YAML 挂到不同 `requests` 的 Deployment 上行为完全不同。**
- [Day 12] 扩容时间线（T0=加压，1 副本，`cpu 0%/60%`）：**T+26 s HPA 决策**（`SuccessfulRescale New size: 3`）、
  T+28 s Pod 创建、T+38–41 s 新副本 Ready 开始接流量、T+77 s 第二次决策、T+87 s 4/4 Ready。
  **滞后 41 s 中有 26 s（63%）花在「指标被看见」这一段**，调度 2 s、拉镜像 0 s（已 `kind load`）、
  启动+加载约 8 s、readiness 约 3 s。
- [Day 12] **扩容过程中出现约 3 秒服务完全不可用**：T+35 s 原健康副本因 readiness 超时被摘出 endpoints，
  新副本 T+38 s 才进来，中间就绪端点数为 **0**，对应压测第一个 60 s 窗口的 3856 个失败
  （其余四个窗口合计只有 1 个）。**「副本数从 1 涨到 4」这张图上完全看不出中间断过。**
- [Day 12] 缩容（停止加压后）：**+306 s 走第一步 4→3，+366 s 3→2，+426 s 2→1**，
  与 `scaleDown.stabilizationWindowSeconds: 300` + `policies: 1 Pod / 60s` 逐条吻合。
  **缩容比扩容慢一个数量级（426 s vs 41 s），而且这是设计意图**（稳定窗口取窗口内最高推荐值，防抖）。
- [Day 12] **三个静默失败**：① `kind load` 的报错被 `tail -1` 吞掉 → metrics-server `ImagePullBackOff`
  → HPA 显示 `<unknown>` 而不报错；② Pod 不 Ready 时 HPA 拿不到指标，只发 `FailedGetResourceMetric`
  Warning，副本数不动；③（未实测，论述）GPU 节点没有空闲卡时 HPA 照样扩，新 Pod 停在 `Pending`。
  **共同点：控制器只负责把期望值写下去，写不下去不是它的错误路径。**
- [Day 12] 实验用的容器环境内**无法运行 dockerd**，且不是「没装」：`capsh --print` 的 bounding set 里没有
  `cap_sys_admin`，cgroup2 只读挂载，`/dev/fuse` 不存在；rootless 退路同样不通
  （`unshare -Ur true` → `Operation not permitted`，`/etc/subuid` 为空）。

## 13. 跨天的可复用方法（不带数字，但每条都由上面某几行支撑）

- **M1 先定噪声地板，再谈有没有效。** [Day 10] 的 1.87% 让「扫了 10 个 NCCL 变量只有 2 个有效」
  成为一条可发表的结论，而不是一堆看起来都有效的小数点。
- **M2 分母必须自己测，且换机重测。** [Day 08] 实测 GEMM 峰值而不抄规格书；
  [Day 10] 换机后 busbw 掉 19.2%、GEMM 涨 8.7%，不重测则全部归因作废。
- **M3 每个数字都要报口径。** 显存三档（F0.3）、MFU 含不含 lm_head（Day 08）、
  aggregate vs per-GPU（Day 10）、镜像三口径（Day 12）、busbw 的 P 系数（Day 09）。
- **M4 用一个独立的物理约束交叉验证。** [Day 01] Little 定律四档 ≤4%；
  [Day 09] 消息大小 ÷ 微基准带宽 vs profiler kernel 时间，偏差 8.7%；
  [Day 10] kernel launch 次数 × 10 µs vs 实测空档，471 vs 463 ms；
  [Day 03] 批内最大值概率 97.2% 预测吞吐比 0.25 vs 实测 0.287。
- **M5 「指定了」不等于「生效了」。** [Day 08] 指定 cudnn 实际跑 flash；
  [Day 09] FSDP 要打印被 wrap 的模块数（实测 29 = 28 层 + 根）确认 policy 生效；
  [Day 09] DeepSpeed 的三个 batch 字段要从 engine 反查而不是相信自己写进 config 的值。
- **M6 失败要留证，不要重试到好看为止。** [Day 06] INT8 全量 QDQ 崩塌的诊断链全部保留；
  [Day 10] 作废的第一版扫描保留在 `invalid_first_sweep/`；[Day 09] 修 bug 前后的两次带宽都保留。
- **M7 先证明，再删除。** [Day 05] 0.000e+00 逐位恒等才是删掉 34.86% 参数的许可证。
- **M8 百分比不能相加。** [Day 10] 跨侧超可加 +90.3 pp、同侧次可加 −6.7 pp，
  分账要用乘法分解（取对数）才顺序无关。
