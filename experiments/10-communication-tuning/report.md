# Day 10 · 通信优化：MFU 从 5.85% 提到 31.82%，其中单卡侧 73%、通信侧 27%

一句话结论：

> **双卡 aggregate MFU 从 5.85% 提到 31.82%（5.44×）。
> 把它拆开：单卡 MFU 从 10.68% 提到 36.85%（贡献 73%），
> 扩展效率从 54.8% 提到 86.4%（贡献 27%）。**

拆解能成立，是因为这两件事是**相乘**的关系：

```
aggregate MFU = 单卡 MFU × 扩展效率
基线   10.68% × 54.8% = 5.85%    ✓
最终   36.85% × 86.4% = 31.82%   ✓
```

这也直接解释了本日的交互作用实验为什么是**超可加**的：
两项各 +88% 的改动叠加后不是 +176% 而是 **+265%**——因为百分比相加
本来就是错误的记账方式。

## 2. MFU 口径与基线

```
MFU = 每 step 总 model FLOPs / (step 时间 × 卡数 × 单卡实测 GEMM 峰值)

每 step 总 model FLOPs = 卡数 × micro_bsz × seq_len × grad_accum × FLOPs_per_token
FLOPs_per_token(seq=512) = 6N + 12·L·d_attn·s = 2.643 G + 0.352 G = 2.995 GFLOPs
N(非 embedding) = 440,467,456    L = 28    d_attn = 16 × 128 = 2048
```

两个必须写明的口径：

1. **aggregate 而不是 per-GPU。** 分母乘了卡数，所以单卡与双卡的 MFU 可直接比较，
   weak scaling 100% 时两者相等。若用 per-GPU 口径（分母不乘卡数），双卡数字会凭空翻倍，
   看上去像"双卡 MFU 更高"，那是记账错误。
2. **不含 lm_head**，沿用 Day 08 的任务书口径。Day 08 已证明这会系统性低估约 23%
   （lm_head 是 `[tokens, 151936]` 的真实矩阵乘）。归因用不含的口径，与 Day 08/09 可比。

**基线（本机重测，seq 512 / micro 2 / k=1）：**

| | 吞吐 | MFU | 扩展效率 |
|---|---|---|---|
| 单卡 | 6,029 tok/s | **10.68%** | — |
| 双卡 DDP | 6,606 tok/s | **5.85%** | **54.8%** |

**双卡把单卡的 MFU 砍掉了 45%，这就是本日的靶子。**

## 3. 噪声地板：先定出"多大的变化才算变化"

配置完全不变，**独立进程**重复 10 次（不是同一进程内的多个 block——
后面比较各配置时每个配置本来就是一个独立进程，噪声地板必须同口径）：

| 统计量 | 中位 | std | 相对 std | 极差 |
|---|---|---|---|---|
| step time | 309.07 ms | 1.507 ms | 0.49% | **1.87%** |
| tokens/s | 6,626 | 32.4 | 0.49% | **1.87%** |
| MFU | 5.87% | 0.029 pp | 0.49% | 1.87% |

> **噪声地板 = 1.87%（吞吐极差口径），2σ 口径 0.98%。**
> 本报告所有 |Δ吞吐| < 1.87% 的改动一律标为「低于噪声地板，不构成结论」。

进程内（block 间）极差是 0.15%–1.26%，**小于进程间的 1.87%**，
说明主要抖动来自进程之间而非步之间——与 Day 08/09 的观察一致。

**`MIN` 与 `MAX` 的区别就是本日最有价值的一条 NCCL 结论。**
`NCCL_MAX_NCHANNELS=8` 只是把上限抬高，NCCL 依旧按自己的拓扑判断选 2 个 channel
（Day 09 日志里的 `Channel 00/02` 就是 2 个），所以毫无效果；
`NCCL_MIN_NCHANNELS=8` 才是**强制**用 8 个，于是把 SHM 路径的并行度打开。细扫确认了机制：

| MIN_NCHANNELS | 2（=默认） | 4 | 8 | 16 |
|---|---|---|---|---|
| 吞吐 | 6,637 | 7,506 | 7,621 | 7,510 |
| Δ | 基线 | **+13.6%** | **+15.4%** | +13.7% |

**收益在 4 个 channel 处几乎全部兑现，8 以后饱和，16 反而略降。**

`NCCL_SHM_DISABLE=1` 掉到基线的 28.8%，反向证明了 Day 09 的 transport 判定：
这条链路确实完全依赖共享主机内存，禁掉后回落到 NET/Socket 就慢 3.5 倍。

`NCCL_PROTO=LL128` 慢 21.1% —— 我预测它是玄学，实测它有害。
LL/LL128 是用冗余标志位换低延迟、为小消息设计的；这里的 bucket 是 25 MB 级，
带宽已饱和，加上标志位开销只会变慢。**"对小消息有效"的旋钮用在大消息上不是无效而是有害。**

## 5. 通信与计算的 overlap（任务书 3.4）

指标：**重叠系数 = Σ(所有 CUDA kernel 自时间) ÷ 干净单步时间**。
NCCL kernel 在独立 stream 上与计算并发，所以该值可以 > 1，超出部分即重叠量；
< 1 则差额是 GPU 真实空泡。干净单步时间取自不挂 profiler 的那次运行（任务书 4.4）。

| 配置 | 通信占 CUDA 时间 | 通信 kernel | 重叠系数 | 结论 |
|---|---|---|---|---|
| 基线 DDP k=1 | 58.13% | 215.3 ms/步 | **1.19** | 重叠了，藏掉相当于单步的 19.4% |
| k=8 | 25.04% | 209.2 ms/步 | **0.64** | **未重叠满，GPU 真实空泡 36.1%** |

### 5.1 bucket 是分批触发还是堆在最后

从 chrome trace 取每个通信 kernel 的相对启动时刻（0 = 步首，1 = 步尾）：

| 配置 | first | p25 | p50 | p75 | last |
|---|---|---|---|---|---|
| 基线 DDP k=1 | 0.00 | 0.19 | 0.48 | 0.78 | 0.90 |
| k=8 | 0.00 | 0.31 | 0.63 | 0.96 | 0.98 |

**DDP 的 bucket 确实在 backward 过程中分批触发，均匀散布在整个 step 上，没有堆在最后。**
这解释了为什么 `bucket_cap_mb` 怎么调都没用——**调度已经是对的，瓶颈不在调度**。
通信时间 215.3 ms 本身就大于可藏的 backward 窗口，粒度再怎么变也藏不完。

### 5.2 k=8 的 36.1% 空泡不是通信造成的

这是本日最容易误读的一个数。先排除"profiler 丢事件"：

```
gemm kernel launches   k=1: 2,109/3步     k=8: 16,872/3步   = 恰好 8 倍 ✓
通信 kernel launches   k=1: 174/3步       k=8: 174/3步      = 完全相同 ✓（no_sync 生效）
```

事件没丢，空泡是真的。来源是 **CPU 下发**：

```
k=8 每个优化器步要发 46,325 次 kernel（k=1 只有 5,879 次）
按约 10 µs/次的下发开销 ≈ 463 ms
实测空档 = 1306.5 − 835.5 = 471 ms
```

**两者吻合。梯度累积把通信瓶颈换成了 kernel launch 瓶颈。**
这直接解释了 k=16 相对 k=8 只多涨 8 个百分点（+89.8% → +97.9%）：
通信已被摊薄到可忽略，新的墙是 CPU。

也因此，**`torch.compile` 在 k=8 上的收益远大于在 k=1 上**：
k=1 时它只值 +8.2%，叠在 mb4+k8 之上时值 **+45.9%**（24,611 → 35,923），
因为它靠算子融合把 kernel 数量压下来，正好打在新的瓶颈上。

## 6. 归因拆解（任务书 3.6）

### 6.1 交互作用：百分比不能相加

A = 梯度累积 k=8，B = micro batch 4：

| | 吞吐 | 相对基线 |
|---|---|---|
| 只加 A | 12,337 tok/s | +86.8% |
| 只加 B | 12,420 tok/s | +88.0% |
| **A + B** | **24,120 tok/s** | **+265.1%** |
| 若可加应为 | — | +174.8% |

**实测比可加假设高 90.3 个百分点——强烈的超可加。**

机制：每优化器步的通信量恒为 `4N = 2.38 GB`，与 batch 无关。
A 把每次 all-reduce 覆盖的 token 数放大 8 倍，B 放大 2 倍，**A+B 放大 16 倍**。
放大倍数是相乘的，而"百分比提升"是对倍数取差，所以相加必然低估。

第二组交互，两项都在通信侧（A = k=8，C = `MIN_NCHANNELS=8`）：

| | 吞吐 | 相对基线 |
|---|---|---|
| 只加 A | 12,337 | +86.8% |
| 只加 C | 7,690 | +16.4% |
| A + C | 12,981 | **+96.5%** |
| 若可加 | — | +103.2% |

**这一组是次可加**（−6.7 pp）：通信一旦被摊薄 8 倍，"让通信更快"能拿到的就自然缩水。

> **两组交互方向相反，正是拆解必须做实验而不能算术相加的理由。**
> 同侧的两项互相挤占（次可加），跨侧的两项互相放大（超可加）。

### 6.2 逐项累加

| # | 配置 | 吞吐 | 双卡 MFU | ΔMFU | 归类 |
|---|---|---|---|---|---|
| 0 | 基线 micro2 k1 | 6,606 | 5.85% | — | — |
| ① | ＋micro batch 4 | 12,374 | 10.96% | **+5.11 pp** | 单卡侧 |
| ② | ＋梯度累积 k=8 | 24,120 | 21.37% | **+10.41 pp** | 通信侧 |
| ③ | ＋`NCCL_MIN_NCHANNELS=8` | 24,611 | 21.80% | +0.43 pp | 通信侧 |
| ④ | ＋fused AdamW | — | — | **OOM** | 单卡侧 |
| ⑤ | ＋`torch.compile` | **35,923** | **31.82%** | **+10.02 pp** | 单卡侧 |

**最终配置：`micro_bsz=4, grad_accum=8, NCCL_MIN_NCHANNELS=8, torch.compile`，
双卡 35,923 tok/s，aggregate MFU 31.82%，显存 17,288 MiB/卡。**

（fused AdamW 单独测时 +12.0% 有效，但叠到 mb4+k8 的显存水位上会 OOM——
它需要额外的连续缓冲。这是一条"单独有效、叠加后放不下"的真实取舍。）

### 6.3 通信侧 vs 单卡侧到底各占多少（预测 5 的检验）

逐项累加的 pp 是**顺序依赖**的（6.1 已证明存在强交互），所以不能直接用它做分账。
用乘法分解才是顺序无关的：

```
aggregate MFU = 单卡 MFU × 扩展效率
```

在同一配置下分别测单卡与双卡：

| 配置 | 单卡 MFU | 双卡 aggregate MFU | 扩展效率 |
|---|---|---|---|
| micro2 k1（基线） | 10.68% | 5.85% | **54.8%** |
| micro4 k1 | 19.94% | 10.96% | 55.0% |
| micro4 k8 | 24.75% | 21.37% | **86.3%** |
| micro4 k8 + compile（最终） | **36.85%** | **31.82%** | **86.4%** |

```
单卡 MFU   10.68% → 36.85%    ×3.451
扩展效率   54.8%  → 86.4%     ×1.577
合计                          ×5.442   （5.85% → 31.82% ✓）

取对数分账（顺序无关）：
  单卡侧  ln(3.451) / ln(5.442) = 1.2387 / 1.6943 = 73.1%
  通信侧  ln(1.577) / ln(5.442) = 0.4556 / 1.6943 = 26.9%
```

> **MFU 从 5.85% 提到 31.82%，其中单卡侧贡献 73%、通信侧贡献 27%。**
> 换算成百分点：单卡侧约 19.0 pp，通信侧约 7.0 pp。

**任务书 3.1 的判断是对的（单卡侧占大头），我的预测 5 错了**（我预测通信侧 51%）。
错因写在 journal。

一个必须点明的细节：**`micro batch 4` 虽然被归在单卡侧，它也在摊薄通信**。
用单卡数据可以把它拆开——单卡上 micro2→micro4 是 +86.6%（纯计算效率），
双卡上是 +88.1%，两者几乎相同，而扩展效率只从 54.8% 动到 55.0%。
**所以在 k=1 时，加大 micro batch 的收益几乎全部来自单卡计算效率，
通信摊薄那一份小到看不见**——因为通信时间（215 ms）远大于计算时间，
摊薄 2 倍不足以改变量级。真正把扩展效率拉起来的是 k=8（55.0% → 86.3%）。

## 7. 换成有 NVLink 的机器，权重会怎么变（任务书 3.7）

用本机实测的 12.37 GB/s 与 NVLink 4.0 的约 900 GB/s 推，比值 **72.8×**。
基线的通信 kernel 时间 215.3 ms/步，按此缩放降到 **2.96 ms**。

| | 本机（SHM 12.37 GB/s） | 外推 NVLink（900 GB/s） |
|---|---|---|
| 基线单步 | 310.0 ms | ≈ 172 ms（单卡 169.9 + 通信 2.96，几乎全藏得住） |
| 基线扩展效率 | **54.8%** | **≈ 98.7%** |
| 基线 aggregate MFU | 5.85% | ≈ **10.54%** |
| 梯度累积 k=8 的收益 | **+89.8%** | ≈ **+1.3%**（扩展效率已无空间） |
| `MIN_NCHANNELS=8` 的收益 | **+15.4%** | ≈ **+0.2%** |
| micro4 + compile 的收益 | 见 6.3，单卡 MFU ×3.45 | **不变，仍是 ×3.45** |
| 最终 aggregate MFU | 31.82% | ≈ **36.4%**（≈ 单卡 36.85% × 98.7%） |

**结论：在 NVLink 机器上，本日通信侧的全部改动价值从 27% 掉到约 2%，
而单卡侧的 73% 一分不少。** 分账会从 73 : 27 变成约 98 : 2。

这条外推还给出一个可证伪的预期：**在 NVLink 上，梯度累积不应该再被当作性能手段**
（它只剩"增大有效 batch"的训练学意义）；而在本机它是单项收益最大的旋钮之一。
**同一个配方在两台机器上的价值差 70 倍——这就是为什么调参清单不能跨机器抄。**

> 本节是**外推不是实测**：本机没有第二种互联可比，900 GB/s 是 NVLink 4.0 的规格值。
> 线性缩放忽略了延迟项与 kernel 启动开销；通信降到几毫秒后这些项会变主导，
> 所以上表的外推值是乐观下界。

  `all_gather_object`，而 rank 1 仍在做梯度 all-reduce，两边集合操作错位，
  NCCL watchdog 等满 600 秒 SIGABRT。该配置的数据由 `inter2_AB_mb4_accum8`
  （完全相同的配置）提供，未重跑。
- **`micro batch 6` 与 `mb4+k8+fused AdamW` 都 OOM**，显存墙的位置与 Day 08 一致。
- **只测了 P=2。** 所有通信量与 busbw 系数都只在双卡下成立；
  `MIN_NCHANNELS` 的最优值（4–8）也可能随卡数变化。
- **只测了一个模型、一个 seq_len（512）。** 6.3 的 73 : 27 分账依赖
  "通信时间远大于计算时间"这个前提；模型更大时计算时间上升，分账会向通信侧偏移。
- **宿主是共享的**（128 核，测量期间 loadavg ≈ 21），噪声地板 1.87% 已把这部分包含在内，
  但极端情况下的长尾未被 10 次重复覆盖。
- **NVLink 外推未经实测**（第 7 节已标注）。
