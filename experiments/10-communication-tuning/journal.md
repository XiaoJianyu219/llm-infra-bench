## 1. 五条预测（任务书 3.1，写于测量之前，不得修改）

### 预测 0（先于一切的噪声地板，任务书 3.3）

**预测：完全不改配置重复 10 次，step time 的相对标准差 < 1%，极差 < 3%。
噪声地板按极差口径定在 2%。**

依据：Day 09 实测 DDP 的 block 间 std 2.6 ms / 267.0 ms = 0.97%；
Day 08 实测非 checkpointing 配置的进程间极差 0.42%–0.64%。
**但 Day 08 也实测到开 gradient checkpointing 后进程间极差跳到 5.99%–10.79%**，
所以如果本日某个配置的重复性突然劣化到 5% 以上，
第一怀疑不是"这个改动有效"，而是"这个改动让重复性变差了"。

### 预测 1 — 当前双卡 MFU 多少？优化后能到多少？

- **当前双卡 MFU ≈ 7.4%**（由 Day 09 数字换算，本机重测后可能有几个百分点出入）。
- **优化后 25%**，区间 **18%–32%**。

推理：单卡 micro4 的 MFU 已经是 22.6%（11,732 tok/s），
单卡 micro6（Day 08 实测 12,591 tok/s @s512）是 24.2%。
**双卡的 aggregate MFU 上限就是单卡 MFU（weak scaling 100% 时相等）**，
所以 25% 意味着我预计能把扩展效率做到 ~100%，即通信几乎完全藏掉。
这在梯度累积 k 足够大时是可达的——k=8 时通信摊到 8 个 micro-step 上。

### 预测 2 — 梯度累积把 all-reduce 频率降到 1/k，吞吐提升多少？

| k | 预测吞吐 | 相对 k=1 |
|---|---|---|
| 1 | 7,671 tok/s | 基准 |
| 2 | 10,700 | **+40%** |
| 4 | 12,400 | **+62%** |
| 8 | 13,300 | **+73%** |

点估计 k=8 为 **+73%**，区间 **+50%…+95%**。

推导（用 Day 09 实测值）：DDP 用 `no_sync()` 关掉中间 micro-step 的 all-reduce 后，
一个优化器步 = k 次纯计算 + 1 次 all-reduce：

```
k=1  单步 267.0 ms / 2,048 token
k=8  8 × 137.7（纯计算，无通信）+ 129（暴露的通信部分）
     = 1,230.6 ms / 16,384 token  →  13,314 tok/s
```

其中「暴露的通信 129 ms」取自 Day 09：单卡 137.7 → DDP 267.0，差 129.3 ms。

**上限是 2 × 单卡 = 14,872 tok/s（+93.9%）**，所以 +95% 是区间上界，不可能超过。

### 预测 3 — `bucket_cap_mb` 调大调小会怎样

**预测：在这台机器上 bucket_cap_mb 的影响很小，最优值在 25–100 MB，
两端的差异大部分低于噪声地板。**

- **调小到 1 MB：变慢 5%–15%。** 梯度总量 2.38 GB，1 MB 一桶就是 2,384 次 all-reduce；
  而 Day 09 实测 1 MB 消息的 busbw 只有 10.67 GB/s，比 1 GB 档的 15.30 低 30%
  （小消息是延迟主导）。桶多带来的重叠机会换不回带宽损失。
- **调大到 200 MB：±3%，大概率低于噪声地板。** 带宽在 16 MB 以上已经饱和，
  再大不涨；粒度变粗理论上会推迟第一个桶的触发时机，但——
- **根本原因**：这台机器的通信时间（169.4 ms）**远大于** backward 的计算时间
  （单步 137.7 ms 里 backward 约占 40%，即 ~55 ms）。
  **能藏的窗口只有 55 ms，而要藏的是 169 ms**，调度粒度怎么调都藏不完。
  bucket_cap_mb 调的是「藏得巧不巧」，而这里的瓶颈是「窗口根本不够大」。

### 预测 4 — 哪些 NCCL 变量真有效、哪些是玄学

**先分类再验证：**

| 变量 | 预测 | 理由 |
|---|---|---|
| `NCCL_BUFFSIZE` | **可能有效**，0%–5% | SHM 路径的流水线缓冲，直接影响分块深度 |
| `NCCL_MAX_NCHANNELS` / `MIN_NCHANNELS` | **可能有效**，0%–8% | Day 09 日志显示只用了 2 个 channel（`Channel 00/02`），提高并行度或许能压榨带宽 |
| `NCCL_NTHREADS` | **可能有效但幅度小**，0%–3% | SHM 路径靠 CUDA kernel 搬数据，线程数影响吞吐 |
| `NCCL_SHM_DISABLE=1` | **有效但反向**，预计慢 2–5 倍 | 禁掉 SHM 会强制走 NET/Socket（Day 09 日志里 `Using network Socket` 是 fallback 路径）。这条是**反向验证**，用来证明 SHM 确实在起作用 |
| `NCCL_ALGO` | **玄学** | P=2 时 Tree 退化为 Ring，没有可选空间 |
| `NCCL_PROTO` | **玄学** | LL/LL128 是为小消息降延迟设计的；我们的桶是 25 MB 级，Simple 已是最优 |
| `NCCL_SOCKET_NTHREADS` | **玄学** | 它只作用于 NET/Socket 路径，而我们走 SHM，根本不经过 |
| `NCCL_NSOCKS_PERTHREAD` | **玄学** | 同上 |

**总预测：8 个变量里只有 2 个（BUFFSIZE、MAX_NCHANNELS）有可能超过噪声地板，
1 个（SHM_DISABLE）会显著变慢，其余 5 个低于噪声地板。**

### 预测 5 — 最终提升里通信侧与单卡侧各占多少（题眼）

口径先定死，否则这一问无法证伪：

- **通信侧** = 减少通信次数或时间的改动：梯度累积、`bucket_cap_mb`、
  `gradient_as_bucket_view`、`static_graph`、NCCL 变量。
- **单卡侧** = 提高单卡计算效率的改动：micro batch size、fused AdamW、TF32、
  `torch.compile`、`set_to_none`。

**预测：通信侧 +9 个百分点（7.4% → 16.4%），单卡侧 +8.6 个百分点（16.4% → 25%），
即通信侧略占大头，约 51% : 49%。**

**我这一条与任务书的判断相反。** 任务书 3.1 写「在这张卡上我的判断是单卡侧占大头」。
我判断通信侧占大头，理由是：双卡相对单卡的 MFU 从 14.32% 掉到 7.38%，
**掉的这 6.94 个百分点百分之百由通信造成**，光把它拿回来就是 +6.9；
而单卡侧的空间是 14.32% → 24.2%（micro2 → micro6），约 +9.9 个百分点，
但它在双卡上不能全额兑现（batch 变大后通信占比下降，两者有交互）。

**这条预测的风险我也先写下**：梯度累积同时增大了有效 batch，
它既降低通信频率（通信侧）又提高单卡计算效率（单卡侧），
**这一项的归属本身就是含糊的**。我把它记在通信侧，
并在 3.6 用「只加 A / 只加 B / A+B」的交互作用实验去量化这个含糊有多大。
若 A+B 的收益明显小于两者之和，说明重叠的那部分正是这个含糊地带。

## 2. MFU 口径（任务书 3.2）

```
MFU = (每 step 的总 model FLOPs) / (step 时间 × 卡数 × 单卡实测 GEMM 峰值)

每 step 总 model FLOPs = 卡数 × micro_bsz × seq_len × grad_accum × FLOPs_per_token
FLOPs_per_token (seq=512, 任务书 Day08 口径) = 6N + 12·L·d_attn·s
                = 2.643 G + 0.352 G = 2.995 GFLOPs
N（非 embedding） = 440,467,456      L = 28     d_attn = 16 × 128 = 2048
```

分母的 **单卡实测 GEMM 峰值本机重测**，不沿用 Day 08 在 bjb1 上测的 155.57 TFLOPS，
也不抄规格书的 165.2。

两个必须写明的口径：

1. **aggregate 而非 per-GPU。** 上式分母里乘了卡数，所以单卡与双卡的 MFU 可直接比较：
   weak scaling 100% 时两者相等。若用 per-GPU 口径（分母不乘卡数），
   双卡的数字会凭空翻倍，看起来像"双卡 MFU 更高"，那是记账错误。
2. **不含 lm_head。** 沿用 Day 08 的任务书口径（6N 只算非 embedding 参数）。
   Day 08 已证明这会系统性低估约 23%（lm_head 是 `[tokens, 151936]` 的真实矩阵乘）。
   本日同时给出含 lm_head 的一列，但归因拆解用不含的那一列，与 Day 08/09 可比。

## 3. Young/Daly 最优 checkpoint 间隔的推导

> **归属说明**：这一节属于 **Day 11 任务书 §2.3**，不在 Day 10 的任务书里。
> 用户明确要求不要跳过这个推导，故在此完成；Day 11 直接引用，
> 届时把本机实测的 δ 代入即可。

### 3.1 设定

- 有用计算以每 `τ` 单位时间保存一次 checkpoint；
- 保存一次的固定开销 `δ`（这段时间不产出有用计算）；
- 故障服从泊松过程，平均故障间隔 `M`（MTBF）；
- 故障后从最近一次 checkpoint 重启，重启本身的固定开销 `R`。

一个「周期」的墙钟时间是 `τ + δ`（先算 τ，再写 δ）。
在 `τ + δ ≪ M` 的前提下，一个周期内发生故障的概率约为 `(τ+δ)/M`。
故障时刻在周期内近似均匀分布，故**期望损失的有用计算是 `τ/2`**。

### 3.2 总开销的期望

完成 `τ` 单位有用计算所需的期望墙钟时间：

```
T(τ) = τ + δ + (τ+δ)/M · [ τ/2 + R ]
        ↑   ↑     ↑          ↑     ↑
      有用  保存  故障概率  重算损失 重启
```

定义「开销率」= 无用时间占有用时间的比例：

```
H(τ) = T(τ)/τ − 1
     = δ/τ + (τ+δ)/(Mτ) · (τ/2 + R)
     = δ/τ + (τ+δ)/(2M) + R(τ+δ)/(Mτ)
```

### 3.3 一阶近似与求极值

在 `δ ≪ τ` 且 `R ≪ M` 时，保留主导项：

```
H(τ) ≈ δ/τ + τ/(2M)
       ↑      ↑
   保存开销  重算损失
   随 τ 变大而减小   随 τ 变大而增大
```

两项一增一减，必有极小。对 τ 求导并令其为零：

```
dH/dτ = −δ/τ² + 1/(2M) = 0
     ⇒ τ² = 2δM
     ⇒ τ_opt = √(2δM)              ← Young/Daly 一阶公式
```

二阶导 `d²H/dτ² = 2δ/τ³ > 0`，确为极小值。

### 3.4 最小开销也有闭式解

把 `τ_opt = √(2δM)` 代回：

```
H(τ_opt) = δ/√(2δM) + √(2δM)/(2M)
         = √(δ/(2M)) + √(δ/(2M))
         = 2√(δ/(2M))
         = √(2δ/M)
```

**最优点上，保存开销与重算损失各占一半**——这是这个模型最好记的一条性质：
如果实测发现某个间隔下"保存花的时间"和"故障重算掉的时间"差很多，
那就还没调到最优。

### 3.5 适用边界与 Daly 的高阶修正

一阶推导用了两个近似：`τ+δ ≪ M`（一个周期内最多一次故障）、
故障时刻均匀分布。当 `δ` 与 `M` 可比时它们都不成立。Daly (2006) 给出高阶形式：

```
δ < 2M 时   τ_opt = √(2δM) · [ 1 + (1/3)·√(δ/(2M)) + (1/9)·(δ/(2M)) ] − δ
δ ≥ 2M 时   τ_opt = M        （故障太频繁，保存就该和故障一样频繁）
```

`δ/(2M)` 很小时方括号趋于 1，退回一阶式。

### 3.6 代入（δ 待 Day 11 实测）

本模型 Qwen3-0.6B 的完整 checkpoint 约 `16N = 9.54 GB`
（bf16 参数 2 + bf16 梯度 2 + fp32 主权重 4 + Adam m 4 + v 4，Day 09 §3 已核）。
写盘速率待实测，下表按 `δ` 参数化：

| δ（保存一次） | M = 1 小时 | M = 1 天 | M = 1 周 |
|---|---|---|---|
| 5 s | τ = 600 s，开销 1.7% | τ = 2,939 s，开销 0.34% | τ = 7,775 s，开销 0.13% |
| 15 s | τ = 1,039 s，开销 2.9% | τ = 5,090 s，开销 0.59% | τ = 13,467 s，开销 0.22% |
| 30 s | τ = 1,470 s，开销 4.1% | τ = 7,200 s，开销 0.83% | τ = 19,047 s，开销 0.32% |
| 60 s | τ = 2,078 s，开销 5.8% | τ = 10,182 s，开销 1.18% | τ = 26,934 s，开销 0.45% |

（`τ_opt = √(2δM)`，`开销 = √(2δ/M)`。）

**可以先读出来的一条**：即使保存一次要 60 秒，只要 MTBF 是一天，
最优间隔也有 2.8 小时、总开销只有 1.2%。
**容错的代价远比直觉小，前提是间隔调对了。**
调错的代价才大——同样 δ=60 s、M=1 天，若每 60 秒存一次，
开销就是 δ/τ + τ/2M ≈ 100% + 0.03% ≈ 100%，**吞吐直接腰斩**。

## 5. 判断错在哪

### 5.1 最大的一处：把"通信造成多少损失"当成了"修通信能拿回多少"（预测 5）

我的推理是：双卡把 MFU 从 10.68% 砍到 5.85%，**掉的这一半百分之百由通信造成**，
所以修通信的空间最大。前半句是事实，后半句是错误推论。

实测的乘法分解：

```
单卡 MFU   10.68% → 36.85%    ×3.451      ← 单卡侧
扩展效率   54.8%  → 86.4%     ×1.577      ← 通信侧
```

通信侧确实把损失基本补回来了（54.8% → 86.4%，已接近 86 的天花板），
**但单卡侧的空间比通信侧大得多，而我在预测时严重低估了它。**

低估的具体来源：我算单卡侧空间时只算了 batch size（10.68% → 19.94%），
忘了 `torch.compile`。而更关键的是——**compile 的价值本身是被通信侧的改动创造出来的**：

```
k=1 时 compile 只值 +8.2%
叠在 mb4 + k=8 之上时值 +45.9%（24,611 → 35,923）
```

因为 k=8 把瓶颈从"通信"换成了"CPU 下发 46,325 次 kernel"（见 report 5.2），
而 compile 正是靠算子融合减少 kernel 数。
**一项优化的价值取决于当前瓶颈在哪，而瓶颈会被另一项优化移动。**
我在做预测时把每一项当成独立的固定收益，这是整条推理里最根本的错误。

### 5.2 把 `MIN_NCHANNELS` 与 `MAX_NCHANNELS` 写成了一条

预测表里我写的是「`NCCL_MAX_NCHANNELS` / `MIN_NCHANNELS` 可能有效 0–8%」。
实测 MAX **+0.2%（玄学）**、MIN **+15.4%（有效）**。

差别在语义：`MAX` 只是把上限抬高，NCCL 依旧按自己的拓扑判断选 2 个 channel；
`MIN` 才是强制下限。**我"预测到了机制（提高并行度有用）却没预测到哪个旋钮能触发它"，
这在实践上等于没预测到**——照着预测去调，我会先试 MAX，看到没用就放弃整条思路。

补扫确认了机制：MIN = 2（默认）/4/8/16 → +0% / +13.6% / +15.4% / +13.7%，
**4 个 channel 就兑现了九成收益**。

### 5.3 "上限 = 2× 单卡"这个断言错了（预测 2d）

我写"weak scaling 100% 时双卡吞吐 = 2× 单卡 = +93.9%，不可能超过"，
但 k=16 实测 +97.9%。

错在**我拿 k=1 的单卡吞吐当 k=16 的上限**。梯度累积在单卡上同样有收益——
它把 AdamW 那一次全参数更新摊到 k 个 micro-step 上。实测单卡
micro4 从 k=1 的 19.94% MFU 涨到 k=8 的 24.75%，**单卡自己就涨了 24%**。
所以 k=16 双卡的正确上限是 `2 × 单卡@k=16`，而不是 `2 × 单卡@k=1`。

**比较扩展效率时，分子分母必须是同一个配置**——Day 09 已经强调过 weak/strong
两种分母不能混用，这次我在第三个维度（k）上又犯了一次同样的错。

### 5.4 用另一台机器的数做预测的基数（预测 1a）

我预测"当前双卡 MFU ≈ 7.4%"，是拿 Day 09 在 bjb1 上的 7,671 tok/s 换算的。
本机实测 5.85%。两台机器：本机 GEMM 峰值更高（169.0 对 155.6 TFLOPS）
但训练吞吐更低（6,029 对 7,436 tok/s）。

**算力更强的机器训练更慢**，这本身印证了 Day 08 的判定（该工作点是 launch 主导），
但也说明：**跨机器搬运一个绝对数去做预测的基数是不成立的**，
哪怕只是用来定"起点"。正确做法是预测"相对基线的变化"，把基线留给实测。

### 5.5 `NCCL_PROTO=LL128` 不是无效而是有害（预测 4e）

我的推理是"LL/LL128 为小消息降延迟设计，我们的 bucket 是 25 MB 级，
Simple 已是最优，所以改了没用"。前半句对，结论错。
LL128 用冗余标志位换低延迟，在带宽已饱和的大消息上，那些标志位是净开销 —— **−21.1%**。

**"针对 X 优化的旋钮，用在非 X 场景下"的默认结果不是"无效"而是"有害"**，
因为优化通常是一种取舍而不是免费的增益。

## 6. 踩的坑

### 6.1 rank 0 单独 OOM，错误路径上的集合操作把作业挂死 600 秒

`stack2_mb4_k8` 跑了 672 秒后 SIGABRT。日志：

```
rank0: Watchdog caught collective operation timeout: WorkNCCL(SeqNum=19, OpType=ALLGATHER, NumelIn=1, NumelOut=2)
rank1: Watchdog ... SeqNum=19, OpType=ALLREDUCE, NumelIn=3146752
rank1: last enqueued work: 75    rank0: last enqueued work: 19
```

rank 0 在第 19 个集合操作上做 `all_gather_object`（我代码里汇总各 rank 显存那一步），
而 rank 1 的第 19 个是梯度 all-reduce。两边**集合操作的序号对上了但类型对不上**。

根因：rank 0 单独 OOM（该配置正好在显存边缘），被我的 `except` 捕获后跳出测量循环、
直接去调 `gather_obj`；rank 1 没 OOM，还在跑剩下的 micro-step。
**"只有部分 rank 会走到的路径上不能有集合操作"**——这与 Day 09 §6.3
（`pcie_bench` 只在 rank 0 跑却内部 barrier）是同一类错误，我隔了一天又犯了一次。

这次没有重跑：该配置的数据由 `inter2_AB_mb4_accum8`（完全相同的参数）提供。
正确的修法是错误路径上不做 gather，直接写本 rank 的结果并立即退出，让 torchrun 去收拾对端。

### 6.2 `pkill -f <脚本名>` 第三次把自己的 shell 杀掉

Day 08 `pkill -f "day08/scripts"`、Day 09 `pkill -f torchrun`、本日
`pkill -f profile_opt.py`——同一条命令里出现了被匹配的字符串，pkill 按 cmdline 匹配，
把执行这条命令的 bash 也杀了（exit 127）。

Day 09 我试过 `[t]orchrun` 的括号写法，**那次也失败了**，因为同一条命令里还有
`/root/.../bin/torchrun` 这个真实路径。
**结论：清理动作必须放在单独一次 SSH 调用里，不要和会提到该名字的命令写在一起。**
写在 `.sh` 脚本里的 `cleanup()` 是安全的（脚本进程的 cmdline 只有脚本路径）。

### 6.3 一开始怀疑 profiler 丢事件，结果是真空泡

k=8 的重叠系数只有 0.64，我的第一反应是"profiler 在 46k 次 launch 下丢事件了"。
核对后发现没丢：gemm launches 是 k=1 的**整整 8 倍**（16,872 对 2,109），
通信 launches 完全相同（174，证明 `no_sync` 生效）。

空泡是真的，来源是 CPU 下发（46,325 次 × ~10 µs ≈ 463 ms，实测空档 471 ms）。
**先怀疑测量工具是对的，但要用可判定的方式去验（数 launch 次数），而不是凭感觉否定数据。**
这条如果糊弄过去，report 里 5.2 那个"梯度累积把通信瓶颈换成 launch 瓶颈"
的核心结论就没有了。

### 6.4 profiler 在最优配置上直接崩了

`micro4 + k=8` 每步约 37 万个 profiler 事件，导出 chrome trace 时 rank 0 退出码 1。
最优配置的 timeline 因此缺失，已记进 report 第 8 节。
**profiler 的可用范围本身是有上限的**，配置越优（kernel 越多）越容易撞到。

### 6.5 显存墙让两个计划中的实验落空

- `micro batch 6` OOM —— 与 Day 08 记录的墙一致，导致原定的交互作用实验

- `mb4 + k8 + fused AdamW` OOM —— fused AdamW 单独测时 +12.0% 有效，

  已写进 report 6.2，没有为了凑一个更好看的数字去降别的参数。
