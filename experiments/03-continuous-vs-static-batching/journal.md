# Day 03 日志

# Day 3 · 连续批处理 vs 静态批处理

一个仅需 32 个输出 token 的请求，在静态批处理下等待 92.6 秒，
而它自身只需要 0.6 秒——被放大 154 倍。本文说明这个放大来自哪里。

## 实验设计

两组服务处理**完全相同**的一份请求序列，仅调度策略不同。

**对照组（静态批处理）**：HF transformers，攒够 16 个请求或等待 50 ms 发一批，
整批一起 prefill、一起 decode，整批同时返回，`max_new_tokens` 取批内最大值。

**实验组（连续批处理）**：vLLM 0.28.0，配置见 `BASELINE.md`。

公平性处理：两组使用同一模型、同一 dtype（bf16）、均启用 KV cache，
对照组亦使用 FlashAttention。差异**仅在调度策略**。
对照组是朴素实现而非劣化实现——其吞吐在定长负载下仅比 vLLM 低 17%，
说明它的算力利用率并不差。

## 负载

```
请求数     200
到达过程   泊松，λ = 4.0 req/s，seed 42
prompt     约 500 token 纯文本（无图像）
输出长度   fixed  : 恒为 128 token
           varlen : 从 {32, 64, 128, 256, 512} 等概率取
```

> 本日为**纯文本负载**，与 Day 1 / Day 2 的多模态负载（512 in + 1 图）
> 不是同一套，两者的绝对值不可横向比较。本日结论建立在组内对照上。

测量机器：见 `results/env/env-day03.txt`。
**四组测量全部在同一台机器上连续完成**，故加速比不受换机影响。

## 结果

| 负载 | 策略 | 吞吐 req/s | makespan | 延迟 p50 | 延迟 p99 |
|---|---|---|---|---|---|
| fixed | continuous | 3.82 | 52.4 s | 2.4 s | 2.5 s |
| fixed | static | 3.27 | 61.2 s | 9.3 s | 14.3 s |
| | **加速比** | **1.17×** | | 3.9× | 5.7× |
| varlen | continuous | 3.45 | 58.0 s | 2.6 s | 12.2 s |
| varlen | static | 0.94 | 212.8 s | 92.8 s | 165.4 s |
| | **加速比** | **3.69×** | | 35.7× | 13.6× |

### 按输出长度分组的延迟中位数

| out_len | n | continuous | static |
|---|---|---|---|
| 32 | 46 | 0.6 s | 92.6 s |
| 64 | 43 | 1.2 s | 94.9 s |
| 128 | 39 | 2.4 s | 94.2 s |
| 256 | 31 | 4.8 s | 82.4 s |
| 512 | 41 | 9.6 s | 82.9 s |

## 结论

**1. 连续批处理的延迟严格正比于请求自身长度。**

continuous 一列中，out_len 每翻一倍，延迟精确翻倍：

```
0.6 / 32 = 1.2 / 64 = 2.4 / 128 = 4.8 / 256 = 9.6 / 512 = 18.75 ms/token
```

每 token 代价是常数 18.75 ms，且截距约为零，说明中位请求几乎无排队。
**每个请求只为自己要的东西付费。**

**2. 静态批处理的延迟与请求自身长度无关。**

static 一列在 82–95 s 之间浮动 13%，无随 out_len 上升的趋势。
32 token 与 512 token 的请求延迟几乎相同——这是"整批同时返回"的直接证据。

**3. 优势主要来自处理长度不均的能力，而非批处理本身。**

定长负载加速比 1.17×，变长负载 3.69×，相差 3.2 倍。
若把连续批处理的价值笼统归于"批处理"，无法解释这个差距。

**4. 定长负载下，代价体现为延迟而非吞吐。**

吞吐仅差 17%，而 p50 差 3.9×、p99 差 5.7×。
静态批处理在计算时 GPU 是满的，算力利用率不低；
它输在请求必须等待攒批、并等整批算完才能返回。
**"加速比"若只报吞吐，会严重低估两者的差距。**

**5. 变长负载下的延迟爆炸是过载的后果，不是批内等待的直接结果。**

因果链：

```
批内 max_new 取最大值（512 步，而非平均 198.4 步）
  → 吞吐从 3.27 降至 0.94 req/s
  → 到达率 4.0 > 服务率 0.94，系统过载 4.3 倍
  → 队列无界增长
  → 延迟从 9.3 s 爆炸到 92.8 s
```

"等最长的"是**起因**，延迟爆炸是**系统过载的后果**。
批时长本身仅 17 s，而中位延迟 92.8 s，两者相差 5 倍以上，
说明延迟的大头是排队积压而非单批等待。

## 交叉验证

**吞吐的塌陷幅度可由批内最大值预测。**

批大小 16、输出长度从 5 个值等概率取，批内最大值为 512 的概率：

```
1 − (4/5)^16 = 97.2%
```

即几乎每批都按 512 步计算。定长为 128 步，故每批时长比约 4×，
吞吐比预测为 0.25。实测 0.94 / 3.27 = **0.287**。

差值来自批时长 = prefill + max_new × 单步时间，其中 prefill
（16 × 500 token）不随 max_new 变化，稀释了比值。

**单个请求的延迟可由批序号预测。**

批时长 = 212.8 s ÷ 12.5 批 ≈ 17 s。第 100 个请求于 t ≈ 25 s 到达，
落在第 7 批，该批于 7 × 17 = 119 s 结束，预测延迟 94 s。
实测 out_len=128 组的中位延迟为 **94.2 s**。

## 实验前预测的更正

**预测一（错）**：定长负载加速比 1.5–2.5×，差距来自攒批等待与批间空档。

实测 1.17×。攒批等待确实发生，但它转化为**延迟**而非吞吐损失。
原预测把两种代价混为一谈。修正：定长负载下连续批处理的价值在延迟侧，
吞吐侧的优势有限。

**预测二（错）**：变长负载下静态批处理的 p99 劣化应比 p50 更严重。

实测方向相反：p50 劣化 35.7×，p99 劣化 13.6×。
原因是静态批处理下**每个请求都被拖累**，中位数直接崩塌，劣化是均匀的；
而连续批处理的 p99（12.2 s）来自 512 token 请求本身的长度，
属负载内生的尾部，不是调度造成的。

修正后的表述：静态批处理的代价均摊在所有请求上，
连续批处理的尾延迟反映负载自身的长度分布。

## 局限

- 对照组的攒批参数（batch 16、window 50 ms）未做敏感性扫描，
  不同取值下的加速比可能变化。
- 静态批处理侧采用离散事件推进时钟、批耗时实测的方式，未走 HTTP，
  故不含网络与序列化开销；连续批处理侧走完整 HTTP 链路。
  该差异对静态批处理有利，故本文报告的加速比是**保守下界**。
- 仅测试了一种到达率（λ = 4.0）。系统在轻载下的差距应显著小于本文结果。
