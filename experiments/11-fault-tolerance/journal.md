## 0. 实验设计（先说清楚，否则预测无法证伪）

任务书 2.2 要求逐位对齐 loss 序列。用 Day 08–10 那套纯随机 token 做不到这件事：
`torch.randint` 造出来的 batch 之间没有结构，loss 恒在 `ln(151936) = 11.93` 附近几乎不动，
**"数据顺序变了"不会在 loss 上留下可辨认的痕迹**，判据就失效了。

所以本日改成一个**有结构的合成语料**：

```
固定 seed 造一个 [n_samples, seq_len] 的 token 数组当作"数据集"（造好后不再变）
sampler 每个 epoch 用 (base_seed, epoch) 生成一个排列 —— 排列本身与全局 RNG 无关，
        这样"数据位置"与"RNG"两种状态可以分别失效、分别观察
模型打开 attention_dropout = 0.1 —— 让全局 RNG 真正进入 forward，
        否则"RNG 没恢复"和"数据没恢复"会退化成同一种故障
```

这样三种 checkpoint 的失效方式互不重叠：

| 版本 | 存了什么 | 预期症状 |
|---|---|---|
| C0 残缺 | 权重 + 优化器 | 数据从头来 + dropout 序列不同 → 偏差大且持续 |
| C1 半全 | ＋数据位置（epoch / 已消费索引） | 只剩 dropout 不同 → 偏差小但持续 |
| C2 完整 | ＋RNG（python/numpy/torch/cuda）＋ scheduler ＋ step 计数 | 逐位一致（或在 bf16 容许误差内） |

**前置条件（任务书 3.5）**：先验证"不中断连跑两次"本身是否逐位一致。
若基线自己就不可复现，2.2 的判据必须改成容许误差，并把误差量级写清。
这一步放在所有对照之前做。

## 1. 四条预测（任务书 2.0，写于测量之前，不得修改）

### 预测 1 — 需要保存哪些状态

**说明先行**：我在写这条之前已经读过任务书 2.1 的清单（读任务书是第一步，无法回避）。
所以这条预测如果只是抄回它的清单，等于没有预测。
我的做法是：**把 2.1 的清单当成给定，预测它还漏了什么**——这才是可证伪的部分。

2.1 已给出的（我认为都必要，不重复论证）：模型权重、优化器状态（含 AdamW 的 m/v/step）、
LR scheduler、四套 RNG、数据加载位置、global step / token 数、GradScaler、配置快照。

**我预测这份清单还漏了三项，而且它们都会在本日的实验里咬人：**

1. **DataLoader worker 进程各自的 RNG。** 任务书把它放在 §3.3 的坑里提了一句，
   但**没有进 2.1 的清单**。`num_workers > 0` 时每个 worker 有独立 RNG，
   主进程的 `torch.get_rng_state()` 救不了它。
   本日若用 `num_workers=0` 则不受影响——**我会显式记录用了几个 worker**，
   不能靠"恰好没踩到"蒙混过关。
2. **梯度累积的中途状态。** Day 10 的最优配置是 `grad_accum=8`。
   若在第 3 个 micro-step 处中断，已累积但尚未 `optimizer.step()` 的梯度会丢。
   清单里"global step"只记优化器步，**记不出 micro-step 的位置**。
   稳妥做法是只在累积边界保存，**而这本身是一条需要写进方案的约束**，不是自动成立的。
3. **决定性开关的快照。** `torch.backends.cudnn.deterministic`、
   `cublas workspace config`、`TF32` 开关。它们不是"状态"但影响可复现性，
   恢复时若与保存时不一致，2.2 的逐位判据会莫名其妙地失败，
   而症状表里的四行**没有一行能对上**。

**另外预测一条排序**：按字节数，checkpoint 的大头是 **AdamW 的 m 与 v（各 4N）**，
两者合计 `8N = 4.77 GB`，占完整 checkpoint（12N = 7.15 GB）的 **66.7%**；
模型权重只占 33.3%；RNG、scheduler、sampler 位置加起来不到 1 KB。
**"checkpoint 太大"这个问题的答案通常是优化器状态而不是模型。**

### 预测 2 — 只存权重+优化器，loss 会差多少

**预测：恢复后第一步的 loss 绝对偏差 |ΔL| = 0.05–0.30，相对偏差 0.5%–3%；
并且这个偏差不会随步数收敛回去，而是持续存在。**

拆成两部分：

- **数据顺序变了（主因）**：C0 恢复后 sampler 从 epoch 0 位置 0 重来，
  喂的是完全不同的 batch。有结构的语料上，不同 batch 的 loss 本身就有差异，
  预计贡献 |ΔL| ≈ 0.05–0.25。
- **dropout 序列不同（次因）**：预计贡献 |ΔL| ≈ 0.005–0.02，一个量级更小。

**症状对应**：任务书的表里这属于"loss 整体偏移 → 数据顺序变了"。
我预测 C0 会同时命中"整体偏移"与"差异很小但持续"两行，
而 C1（补上数据位置）只剩后者。

### 预测 3 — checkpoint 写一次要多久，占 step time 多少

```
完整 checkpoint 体积 = 参数 4N + Adam m 4N + Adam v 4N = 12N
                    = 12 × 596,049,920 = 7.15 GB
```

- **预测 δ（同步写，含 `torch.cuda.synchronize` 与 GPU→CPU 搬运）= 6 秒**，
  区间 **3–15 秒**。依据：7.15 GB，先要 D2H 搬 7.15 GB（实测 H2D/D2H ≈ 25 GB/s → 0.3 s），
  瓶颈在写盘；`/root/autodl-tmp` 是 md0 RAID，估写入 1–2 GB/s。
- **占 step time 的比例**：Day 10 最优单卡配置单步 787.7 ms，
  所以 **δ ≈ 7.6 个 step**，即"每存一次相当于白跑 7.6 步"。
- **异步写**（另起线程 / `torch.save` 到已在 CPU 的副本）预计能把**阻塞时间**
  压到 **0.3–0.8 秒**（只剩 D2H 那一段），但总 I/O 时间不变。

### 预测 4 — 最优保存间隔大概多少步

用 Day 10 journal 第 3 节已推完的 Young/Daly：`τ_opt = √(2δM)`，最小开销 `√(2δ/M)`。
代入预测的 δ = 6 s、单步 0.7877 s：

| M（MTBF） | τ_opt（秒） | τ_opt（步） | 最小开销 |
|---|---|---|---|
| 1 小时 | 208 s | **264 步** | 5.8% |
| 1 天 | 1,018 s | **1,293 步** | 1.18% |
| 1 周 | 2,694 s | **3,420 步** | 0.45% |

**预测：在单机这种量级（MTBF 以天计）最优间隔是 1,000 步上下**，
而任务书 2.3 要扫的 10 / 50 / 200 / 1000 步里，**只有 1000 那一档接近最优，
前三档都是过度保存**。我预测扫描曲线会显示：每 10 步存一次会让吞吐掉到
`1/(1+δ/(10×0.7877)) = 1/(1+0.762) = 57%`，即**吞吐几乎腰斩**；
每 1000 步存一次的损失只有 0.76%。

### 预测 5（2.4 掉卡，虽然任务书 2.0 没列，但它是本日唯一需要双卡的部分）

- **剩下的 rank 不会立刻报错，会卡在 all-reduce 上**，直到 NCCL watchdog 超时。
- **超时时长 10 分钟（600 秒）**，由 `TORCH_NCCL_TIMEOUT_MS`（旧名
  `NCCL_TIMEOUT` / `TORCH_NCCL_BLOCKING_WAIT` 相关）控制，
  默认值我预计是 600000 ms。
  依据：Day 09 与 Day 10 各出现过一次集合操作错位，日志里写的都是
  `Timeout(ms)=600000` 且 `ran for 600035 milliseconds before timing out`。
  **这条我有直接的旁证，属于低风险预测。**
- **超时后进程以 SIGABRT（exitcode -6）结束**，不是干净退出。
- `torchrun --max-restarts=N` 能把整个作业重新拉起，**但恢复点是脚本的入口**，
  即"从 checkpoint 加载"这段逻辑必须是我自己写的；torchrun 不知道训练状态。

## 5. 判断错在哪

### 5.1 最重要的一处：没区分"进程死了"和"进程还活着但不响应"（预测 5a）

我写的是"剩下的 rank 不会立刻报错，会卡在 all-reduce 上直到 NCCL watchdog 超时"，
并且给了 600 秒这个数。实测：

```
kill -9   → torchrun 的 elastic agent 0.44–0.47 秒内察觉子进程退出，整组 SIGTERM。
            NCCL 超时机制根本没被触发。
SIGSTOP   → agent 看不出异常（进程还在），rank0 卡在 all-reduce，
            恰好等满 timeout（30,074 / 60,040 ms）才报错，之后还有约 92 秒尾巴。
```

错的根源是**我只想着 NCCL 这一层，忘了上面还有一层 elastic agent 在监控子进程**。
这两条路径的发现时延差了三个数量级（0.47 s 对 ~692 s），
而真实集群里"卡挂了"更接近 SIGSTOP 那一类（节点失联、GPU 掉出总线、进程假死），
**用 `kill -9` 做掉卡演练会得到一个过于乐观的结论**。

顺带一提，`TORCH_NCCL_ASYNC_ERROR_HANDLING=0` 我也只在 kill -9 下测了，
而那正是这个开关不起作用的场景——该测的 SIGSTOP 场景反而没测（已记入 report 局限）。

### 5.2 `TORCH_NCCL_TIMEOUT_MS` 是我编出来的（预测 5c）

预测里我写"超时由 `TORCH_NCCL_TIMEOUT_MS`（旧名 NCCL_TIMEOUT / BLOCKING_WAIT 相关）控制"，
还给自己找了个理由说"Day 09/10 的日志里都写着 Timeout(ms)=600000，属于低风险预测"。
**日志里那个数是真的，但它来自哪个旋钮我从没验证过。**

实测：`libtorch_cuda.so` 里读取的 24 个 `TORCH_NCCL_*` 变量中没有这一个，
`.py` 里也是 0 处。集合超时只能通过 `init_process_group(timeout=timedelta(...))` 传。
第一版超时实验因此整个作废——我设了一个不存在的变量，实际跑的还是 600 秒默认值，
被我套在外面的 `timeout 260` 提前杀掉，看起来像"超时没生效"。

**"日志里出现过这个数"不等于"我知道哪个参数控制它"。** 任务书 3.7 那条纪律
（不确定的 API 先打印真实接口）我在别处执行了，偏偏在这条自以为有旁证的地方跳过了。

### 5.3 c0 的偏差低估了一个量级（预测 2）

我预测 0.05–0.30，实测 2.911。两个原因：

1. **我把"数据顺序变了"想成"换了一批同分布的 batch"**，实际是 sampler 倒回 epoch 0 位置 0，
   喂的是模型刚刚训练过的那几批，loss 明显偏低——不是随机扰动，是系统性偏移。
2. **c0 也没有恢复 LR scheduler**，而我在预测里只考虑了数据和 dropout 两项。

第 2 点还导致 c1 出现了症状表里没有的一行：**首步只差 0.04，之后单调放大到 0.53**。
这不是"只有前几步差"（step 计数），也不是"整体偏移"（数据顺序），
而是 **LR 预热被重置后更新幅度持续偏小**。

### 5.4 漏了"逐 rank RNG"（预测 1e）

我在预测 1 里特意说"把 2.1 的清单当成给定，预测它还漏了什么"，列了三项，
**其中没有这一项**——而它是本日唯一一个真的把逐位对齐打破了的缺失。
2.4-C2 实测：恢复后 rank0 的 loss 与掉卡前完全一致，rank1 差了 0.045。
因为 checkpoint 只由 rank0 写，`rng_state()` 抓的是 rank0 自己的四套 RNG。
补一份逐 rank 的旁路文件后，两个 rank 都逐位对齐（2.4-C3）。

**"只让 rank 0 写文件"这条纪律（Day 09 任务书 4.2）对结果文件是对的，
对状态文件是错的**——状态里凡是每个 rank 各有一份的东西，都必须每个 rank 各存一份。

## 6. 踩的坑

### 6.1 A 组和 B 组跑在不同的确定性设置下，害我差点误判 c2

第一轮 c2 的最大差是 9.7e-3，比默认模式的噪声带（2.96e-3）还大 3 倍，看上去像"完整 checkpoint 也没能对齐"。
核对参数才发现：我给 B 组的公共参数变量加了 `--deterministic 1`，
但 A 组那条命令是单独写的，替换没匹配上，**A 组跑的是非确定模式**。
补跑 A 组后 c2 立刻变成 0.0。

**对照实验的两组共用参数必须从同一个变量来**，分开写就迟早会漏。

### 6.2 在优化器状态还不存在的时候去测 checkpoint 体积

第一版 `--bench-save` 在训练循环之前执行，那时 AdamW 的 m/v 还没分配，
存出来只有权重（2.38 GB），于是"优化器占 0%、模型占 126%"这种自相矛盾的数字。
126% 是第二个错：`tie_word_embeddings` 让同一块权重在 `state_dict` 里出现两次，
我按 numel 累加就重复计了 155.6M 参数，而 `torch.save` 只存一份。

改成先训 2 步再测，并按 `data_ptr` 去重，才得到 33.3% / 66.7%。
**"占比加起来超过 100%"是最容易被忽略的自检信号**，和 Day 08 那次带宽超过理论值是同一类。

### 6.3 第一版保存间隔扫描每档只跑 ≤40 步

任务书要扫 10 / 50 / 200 / 1000 步，我为了控制时长把每档的总步数封顶在 40，
结果 50 步以上的三档一次都没存过，"相对无保存 −3.5%"这种负开销就是这么来的。
作废后移到 `results/runs/invalid_first_sweep/` 保留。
按 1.27 s/步，跑满 1000 步间隔要 21 分钟一档，改为实测 2/4/8/16 步 + 公式外推。

### 6.4 弹性重启第一次没真的触发 kill

2.4-C 用的 `--auto-resume` 会挑目录里最新的 `.pt`，而那个目录里有 B 组遗留的 `ck_c2.pt`（step 8），
于是作业从 step 8 起步，`--kill-at 4` 这个条件永远不成立，整轮跑完一次 kill 都没发生。
换成干净的独立目录重做（2.4-C2）才看到真实的重启时间线。
**"自动挑最新"这种便利逻辑在实验环境里会悄悄跨实验串台。**

### 6.5 `warn_only=True` 不会让算法变确定

`torch.use_deterministic_algorithms(True, warn_only=True)` 跑完两次仍不一致（最大差反而涨到 1.02e-2），
步时只慢 0.4%——因为它只打告警、不切换实现。PyTorch 的告警原文其实已经把答案写在里面了
（`To explicitly enable determinism call torch.use_deterministic_algorithms(True, warn_only=False)`），
是我第一次没读完就往下走。改成 `warn_only=False` 后逐位一致，代价 +2.4%。

### 6.6 "阻塞耗时"那个字段测的不是我以为的东西

我在 `save_ckpt` 里把"组装 blob 的时间"当作异步写的阻塞下界，测出 0.004 s。
但 `state_dict()` 只返回张量引用，GPU→CPU 的搬运发生在 `torch.save` 内部，
所以那 0.004 s 只是建了个字典。**这个字段名起错了，数字本身没有意义**，
report 里已改成按 D2H 带宽推算，并明确标注异步写未实测。

### 6.7 shell 脚本被写成 CRLF

我用 Python 以文本模式改写 `.sh` 时，Windows 把 `\n` 写成了 `\r\n`，
bash 直接报 `syntax error near unexpected token $'do\r'`。

### 6.8 第一次弹性重启失败在 DDP 的参数校验上

2.4-C3 里 torchrun 的第一次重启起来后，rank1 在 `DDP.__init__` 的
`_verify_params_across_processes`（一个集合操作）上失败，约 67 秒后 exitcode 1；
第二次重启才成功。原因没有进一步定位（大概率是前一次被 kill 的进程留下的资源还没完全释放）。
实践结论：**`--max-restarts` 至少要留 2 次余量**，只给 1 次这轮就直接失败了。
