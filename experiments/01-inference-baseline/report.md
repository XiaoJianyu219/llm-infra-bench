# Day 1 · 推理性能基线

## 目的

在不做任何优化的配置下量化服务现状：显存如何分配、并发提升时吞吐与延迟
如何变化、以及测量本身的可信度有多高。

本日不调任何参数。配置见 `BASELINE.md`。

## 测量协议

- 每档正式测量前跑 20 条 warmup 并丢弃，排除 CUDA graph 捕获与懒加载开销
- 每档 3 次重复取中位数，不取最优值
- 显存由 nvidia-smi 每 0.5 s 后台采样，取压测进行中的最大值
- 固定 seed 42
- 各档请求数：conc 1 / 4 / 16 / 64 分别为 30 / 60 / 150 / 300
  （低并发下单请求耗时长，按并发缩放以控制总时长）

## 显存分解

| 项 | 大小 | 占比 |
|---|---|---|
| 权重（含 non-torch） | 16.79 GiB | 75.6% |
| 峰值激活 | 2.26 GiB | 10.2% |
| CUDA Graph | 0.12 GiB | 0.5% |
| KV cache | 3.05 GiB | 13.7% |
| 合计 | 22.22 GiB | — |
| 启动时卡上可用 | 23.13 GiB | — |

关键区分：**权重被所有请求共享，只占一份；KV cache 每个请求独占一份。**
因此并发上限由 KV cache 容量决定，与权重大小无关。

## KV cache 的理论与实测

实测：`Available KV cache memory: 3.05 GiB`，`GPU KV cache size: 22,208 tokens`

```
3.05 GiB ÷ 22,208 tokens = 144 KiB/token
```

理论：

```
每 token 字节数 = 2(K和V) × 层数 × KV头数 × head_dim × 精度字节数
                = 2 × 36 × 8 × 128 × 2
                = 147,456 B = 144 KiB
```

两者一致。

**GQA 的收益可由此直接量化**：该模型有 32 个注意力头但仅 8 组 KV。
若为标准 MHA（32 组 KV），每 token 开销为 576 KiB，
同样 3.05 GiB 仅能容纳 5,552 tokens。GQA 使可服务上下文提升 4 倍。

## 交叉验证：Little 定律

排队论要求：平均驻留时间 = 并发数 ÷ 吞吐。
该值应约等于 TTFT 加上 decode 总时长。

| conc | 并发 ÷ 吞吐 | TTFT + 127 × TPOT | 偏差 |
|---|---|---|---|
| 1 | 2.38 s | 2.43 s | 2.0% |
| 4 | 2.94 s | 2.92 s | 0.7% |
| 16 | 4.64 s | 4.46 s | 3.8% |
| 64 | 18.18 s | 17.93 s | 1.4% |

四档全部吻合在 4% 以内。四个指标并非各自独立测得，
它们之间的约束关系成立，说明本组测量自洽。

## 结论

**1. 吞吐在并发 16 附近饱和。**
16 → 64 时吞吐仅增 2%（3.45 → 3.52 req/s），而 TTFT_p50 增长 16.4 倍
（844 → 13,814 ms）。饱和后增加并发只延长排队，不增加有效产出。

**2. 瓶颈在排队而非生成。**
TPOT 从 17.3 增至 32.4 ms（不足 2 倍），远小于 TTFT 的 16 倍增幅。
decode 阶段本身未被压垮，等待发生在请求进入批次之前。

**3. 单请求 decode 受显存带宽支配。**
conc 1 的 TPOT 为 17.3 ms。理论下限为权重读取时间：
17.9 GB ÷ 1008 GB/s ≈ 17.8 ms。两者吻合，说明此时算力大量闲置。
这是批处理能近乎免费提升吞吐的原因。

**4. nvidia-smi 观测不到 KV cache 的实际使用量。**
显存峰值在 conc 16 与 64 完全相同（22,215 MiB），因为 vLLM 在启动时
一次性预分配整个 KV cache 池。conc 1 → 16 的 338 MiB 增幅来自激活显存。
若需观测池子的真实占用率，须读取服务的 `/metrics`
（`gpu_cache_usage_perc`），而非 nvidia-smi。

## 更正（Day 2 补记）

结论 1 需要限定条件：本日测量使用 `max-num-seqs=16`，
调度器同时处理的序列数被人为限制。Day 2 对照显示：

```
max-num-seqs 16 → 64：conc 64 吞吐 3.32 → 3.60 req/s（+8.4%）
再放宽至 256：无进一步增益
```

修正后的结论：饱和现象真实存在，但本日的饱和点被 max-num-seqs
额外压低了约 8%。真正的限制因素是 KV cache 容量，
详见 `reports/day02_params.md`。

原始数据与原结论保留不动，供追溯。

## 局限

- 本日未计算噪声底（使用了未含波动统计的汇总脚本版本）。
  同配置的噪声底由 Day 2 的 base 行给出：conc16 为 5.0%，conc64 为 0.1%。
- 各档请求数不同（30 / 60 / 150 / 300），跨档比较吞吐时须注意
  该差异可能引入的爬坡与排空占比偏差。Day 2 起统一为 150。
- 结论 1 的"饱和"为间接推断，未采集压测进行中的
  `num_requests_waiting` 与 `gpu_cache_usage_perc` 作为直接证据。
